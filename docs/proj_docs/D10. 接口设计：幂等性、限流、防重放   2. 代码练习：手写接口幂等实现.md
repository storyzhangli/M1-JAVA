### 模块一：接口设计基础与HTTP幂等语义
#### 1.1 核心定义
- **API（应用程序编程接口）**：不同软件系统之间交互的约定与接口，定义请求格式、响应格式、业务语义与错误码，是系统间协作的契约。
- **幂等性（Idempotency）**：同一个操作执行一次和执行多次，对资源的最终影响完全相同；重复请求不会产生额外的业务副作用，最终状态与单次执行一致。

#### 1.2 四个易混淆概念的区分
| 概念                           | 定义                                   | 关注点                |
| :----------------------------- | :------------------------------------- | :-------------------- |
| 同一个请求被发送多次           | 网络层面重复投递相同的请求报文         | 传输层/网关层面的重复 |
| 同一个业务操作被执行多次       | 服务端重复执行业务逻辑，产生重复副作用 | 业务层面的重复执行    |
| 多次请求返回相同响应           | 响应报文内容一致                       | 响应表现，不等于幂等  |
| 多次请求产生相同的业务最终状态 | 执行后资源最终状态一致                 | 幂等的核心判定标准    |

> 核心结论：幂等性看的是**业务最终状态**，不是响应报文是否相同；成功响应可以有差异，但资源最终状态必须一致。

#### 1.3 HTTP方法的幂等语义
官方参考：**RFC 9110 HTTP Semantics | HTTP语义**：[https://www.rfc-editor.org/rfc/rfc9110.html](https://www.rfc-editor.org/rfc/rfc9110.html)

| HTTP方法   | 协议幂等性             | 语义说明                                                     |
| :--------- | :--------------------- | :----------------------------------------------------------- |
| GET / HEAD | ✅ 天然幂等（安全方法） | 仅获取资源，不修改服务端状态；重复调用无副作用               |
| PUT        | ✅ 协议幂等             | 整体替换资源；相同内容重复PUT，最终状态一致                  |
| DELETE     | ✅ 协议幂等             | 删除指定资源；重复删除最终状态一致                           |
| POST       | ❌ 协议非幂等           | 通常用于创建资源或执行操作；重复POST会创建多个资源或多次执行操作 |

> 重要说明：协议层面的幂等 ≠ 业务层面的幂等。POST可以通过应用层设计实现业务幂等；反过来，即使是GET方法，如果业务实现有副作用（比如统计点击量），也不具备业务幂等。

#### 1.4 重复请求产生的完整链路
重复请求不是只由“用户重复点击”导致，完整链路包含：
1. **客户端层**：用户重复点击、前端重试逻辑、超时自动重试。
2. **网络层**：网络抖动丢包、网关重传、TCP重传。
3. **服务治理层**：调用方框架重试机制（如Feign重试）、消息队列重投。
4. **响应丢失场景**：服务端已经执行成功，但响应报文在返回途中丢失，客户端超时后重试，导致服务端二次执行。

> 最隐蔽也最危险的是「成功执行但响应丢失」：服务端已经完成业务，客户端没收到响应就重试，这时候如果没有幂等控制，业务会被执行两次。

#### 1.5 必须回答的核心问题
1. **为什么创建订单接口通常需要考虑幂等性？**
   创建订单是写操作，POST天然非幂等；客户端超时重试、网络丢包、用户重复提交都会导致重复请求；如果没有幂等控制，会生成多个重复订单，造成重复扣款、重复扣库存等业务问题。

2. **为什么给Controller加synchronized不能可靠解决多实例部署下的重复请求？**
   synchronized是单JVM内的锁，分布式部署下多个实例各自独立，请求可以落到不同节点，完全绕开锁；而且锁会严重影响吞吐量，也无法解决跨实例的并发问题。

3. **为什么前端按钮禁用不能替代服务端幂等控制？**
   前端禁用只能防止用户手动重复点击，无法控制网络重传、客户端重试、脚本重放、网关重发等服务端不可控的重复请求；前端控制是体验优化，不是可靠的正确性保证。

4. **为什么重复请求返回的HTTP响应不必与第一次完全一致，但业务最终效果应符合约定？**
   幂等保证的是业务最终状态一致，不是响应报文完全相同；比如第一次返回201创建成功，第二次可以返回200已存在，只要订单只创建一次，业务状态一致即可。

5. **幂等控制与数据库唯一约束是什么关系？**
   数据库唯一约束是实现幂等性的底层可靠机制，通过数据库层面的唯一性保证，强制同一个业务标识只能写入一次；应用层的幂等键最终落地到数据库唯一约束，才能在并发场景下可靠生效。

### 模块二：接口幂等性的实现方案与关键机制
#### 2.1 常见实现方案对比
##### 方案1：数据库唯一约束
- **原理**：在数据库建立唯一索引，同一个幂等键只能插入一条记录；重复插入时触发唯一键冲突，从而阻止重复执行。
- **流程**：请求到达 → 尝试插入幂等记录 → 成功则执行业务 → 更新幂等记录为成功；插入失败则说明已处理，直接返回已有结果。
- **优点**：数据库级别的原子保证，并发可靠；实现简单，不依赖中间件；事务一致性好控制。
- **缺点**：只能防重复，无法限制并发访问量；数据库有写入开销；高频场景下冲突异常多。
- **适用场景**：核心业务写操作、订单、支付等对正确性要求极高的场景。

##### 方案2：基于数据库幂等记录表的持久化控制
- **原理**：独立幂等记录表，记录每个幂等键的处理状态、结果、时间；业务执行前后操作幂等记录。
- **状态**：PROCESSING（处理中）、SUCCEEDED（成功）、FAILED（失败可重试）。
- **优点**：状态清晰，可保存业务结果，支持重复请求直接返回结果；可追溯、可清理。
- **缺点**：需要独立表；并发下先查后插存在竞态条件，必须配合唯一约束使用。
- **适用场景**：需要返回重复请求相同结果、需要状态追踪的业务接口。

##### 方案3：Redis SET NX原子占位
- **原理**：使用`SET key value NX EX seconds`原子命令，key存在则设置失败，不存在则设置成功；利用Redis单线程原子性保证占位唯一。
- **优点**：性能高，Redis操作快；支持过期自动清理；实现简单。
- **缺点**：仅占位，不保存业务结果；Redis故障可能导致幂等失效；和业务数据库天然不一致，无法保证原子提交。
- **适用场景**：高频轻量校验、前置防重、限流前置的幂等预检；不适合核心业务数据的最终一致性保证。

##### 方案4：Redis Lua脚本原子检查与更新
- **原理**：将检查状态、更新状态多个操作写在Lua脚本中，Redis单线程执行Lua，保证整个检查+更新的原子性。
- **优点**：多个操作原子执行，避免竞态条件；比多次Redis调用性能好。
- **缺点**：调试复杂；和业务数据库仍然是两个系统，无法跨系统事务。
- **适用场景**：Redis内部多步状态流转、计数、限流等原子操作场景。

##### 方案5：Spring AOP/拦截器/自定义注解封装
- **原理**：通过AOP拦截标注了幂等注解的方法，统一提取幂等键、执行幂等校验、处理异常，业务代码无感知。
- **优点**：业务代码解耦，统一处理，复用性好。
- **缺点**：属于应用层封装，底层仍然依赖数据库或Redis的幂等实现；封装不当容易出现事务边界错误。
- **适用场景**：项目统一幂等规范，大量接口需要统一幂等处理。

##### 方案6：业务状态机与条件更新
- **原理**：业务状态只有特定流转路径，更新时加状态条件（`where status = '待处理'`），只有符合前置状态才更新，重复更新影响行数为0。
- **优点**：贴合业务语义，天然幂等；不需要额外幂等表。
- **缺点**：只能处理状态流转场景；并发下可能出现更新失败，需要重试。
- **适用场景**：订单状态流转、审批流程等有明确状态机的业务。

##### 方案7：消息消费场景的事件ID去重
- **原理**：消息自带唯一事件ID，消费前先校验是否已消费，消费成功记录消费状态。
- **优点**：消息系统天然重试场景适配；可结合消息幂等语义。
- **缺点**：需要独立去重存储；并发消费同样需要唯一约束。
- **适用场景**：MQ消息消费、事件驱动架构。

#### 2.2 幂等键设计
##### 什么是幂等键
唯一标识一次业务请求的标识，是幂等控制的核心。通过它判断“是不是同一次请求”。

##### 设计原则
1. **高区分度**：必须能唯一区分不同的业务请求，不能用订单金额、商品数量等低区分度字段。
2. **作用域隔离**：必须包含业务维度（租户/用户ID + 接口标识 + 业务幂等键），不同用户、不同接口使用相同的业务编号互不影响。
3. **请求绑定**：必须绑定完整的请求语义，相同幂等键对应相同的请求内容；参数变了幂等键必须变。
4. **不可逆映射**：不能直接用原始请求体当键，通过哈希摘要（如SHA-256）生成固定长度的摘要。
5. **安全长度**：数据库索引长度有限，控制键长度，避免无限长输入。
6. **有效期与清理**：设置合理保留期，定期清理历史记录，避免表无限膨胀。

##### 标准设计示例
`幂等键 = 租户ID + ":" + 接口编码 + ":" + 客户端生成的请求唯一标识`
- 请求内容校验：对请求体计算哈希摘要，和幂等记录中的摘要比对，防止相同键携带不同参数。

##### 常见错误
- ❌ 直接用订单号等业务字段当幂等键：业务字段重复会误判。
- ❌ 不加作用域直接用随机ID：不同用户冲突。
- ❌ 直接用原始请求体当键：长度不可控、有敏感信息、格式变化导致哈希不一致。
- ❌ 无限期保留：表无限增长，性能下降。

#### 2.3 幂等记录状态与转换
| 状态       | 含义                           | 转换触发                               |
| :--------- | :----------------------------- | :------------------------------------- |
| PROCESSING | 处理中，请求已接收正在执行业务 | 首次请求，插入幂等记录                 |
| SUCCEEDED  | 处理成功，业务已完成           | 业务执行成功，更新幂等记录             |
| FAILED     | 处理失败，可重试               | 业务执行失败，更新幂等记录，释放幂等键 |

##### 核心规则
- 重复请求命中PROCESSING状态：返回「处理中，请稍后查询」，不重复执行业务。
- 重复请求命中SUCCEEDED状态：直接返回已保存的业务结果。
- 失败请求的幂等记录：保留可重试标识，允许客户端使用相同幂等键重试。
- 绝对不能：失败了还保留SUCCESS状态，或者业务失败但幂等记录显示成功。

#### 2.4 数据库唯一约束与事务一致性
##### 为什么先查后插存在竞态条件
两个并发请求都先查询「有没有记录」，都查到没有，然后都执行插入，其中一个成功，另一个失败。如果没有数据库唯一约束，两个请求都会执行业务逻辑，导致重复执行。
> 结论：**唯一性必须由数据库约束保证，不能只靠Java代码判断**。应用层检查只能降低概率，不能杜绝。

##### 事务一致性原则
幂等记录与业务数据必须在**同一个数据库事务**中提交：
- 业务成功 → 幂等记录设为成功，一起提交。
- 业务失败 → 整个事务回滚，幂等记录一起回滚，不会残留成功记录。
- 唯一键冲突异常 → 事务回滚，然后查询已存在的成功记录返回。

> 关键注意：捕获唯一键冲突异常后，**不能继续使用当前事务**，当前事务已经被标记为回滚；必须开启新事务查询已有结果。

##### 跨系统副作用的边界
数据库事务只能保证本地数据库操作的原子性，无法保证远程HTTP调用、支付、消息发送等外部操作和本地事务同时成功/失败。
- 解决方案：事务型发件箱（Transactional Outbox）、下游幂等、补偿机制。
- 本阶段核心：本地业务数据与幂等记录必须事务一致；跨系统问题单独处理。

#### 2.5 Redis实现及其限制
1. **SET NX的原子性**：`SET key value NX EX seconds`是原子命令，Redis单线程执行，保证只有一个客户端能设置成功。
2. **TTL的作用**：自动过期，避免死锁；但过期时间必须大于业务最长执行时间，否则业务还没做完键就释放了。
3. **为什么多步操作需要Lua**：多次Redis调用之间不是原子的，中间可能被其他请求插入；Lua脚本把多步操作打包成一个原子执行单元。
4. **Redis+业务数据库的一致性问题**：Redis和MySQL是两个独立系统，无法跨系统事务；可能Redis占位成功但数据库事务失败，或者数据库成功但Redis没释放。
   - 处理：业务失败要主动删除Redis键；设置合理TTL兜底。
5. **常见风险**：Redis宕机导致幂等失效、网络超时导致重复释放、锁提前过期。
6. **定位**：Redis适合做前置高频校验、限流、轻量幂等；核心业务正确性必须落数据库。

### 模块三：接口限流
#### 3.1 限流的目的与概念区分
##### 什么是限流
控制单位时间内的请求数量/资源消耗，保护服务不被流量冲垮，保障服务可用性和公平性。

##### 概念区分
| 概念       | 核心目标                 | 作用维度             |
| :--------- | :----------------------- | :------------------- |
| 幂等控制   | 防止重复执行业务         | 业务正确性           |
| 限流       | 控制请求频率/资源量      | 服务可用性、资源保护 |
| 熔断       | 故障时切断调用，防止雪崩 | 故障容错             |
| 并发数限制 | 控制同时处理的请求数     | 连接/线程资源        |
| 业务配额   | 控制用户/租户的总量额度  | 业务运营             |

> 关键说明：就算有幂等控制，攻击者用大量不同的幂等键请求，还是会耗尽服务资源，所以限流是独立的保护层。

#### 3.2 常见限流算法
##### 1. 固定窗口计数器
- **原理**：把时间切成固定窗口，每个窗口内计数，超过阈值就拒绝。
- **数据结构**：计数器+时间戳。
- **优点**：实现简单，内存小。
- **核心问题**：窗口边界突刺：两个窗口交界处，前后半分钟各来一倍流量，短时间内流量是阈值两倍。
- **场景**：精度要求不高、流量平稳的场景。

##### 2. 滑动窗口计数器/滑动日志
- **原理**：记录每个请求的时间，每次计算当前往前推一个窗口内的总数。
- **优点**：没有固定窗口的边界突刺问题，精度高。
- **缺点**：需要保存所有请求时间，内存开销大；计算量大。
- **场景**：精度要求高的限流场景。

##### 3. 漏桶算法
- **原理**：水（请求）倒入桶里，桶以固定速率漏水（处理请求）；水满了就溢出（拒绝）。
- **优点**：平滑处理请求，输出速率恒定；适合削峰填谷。
- **缺点**：无法应对突发流量，空闲时也浪费处理能力。
- **场景**：要求输出速率平稳的场景。

##### 4. 令牌桶算法
- **原理**：桶里按固定速率放令牌（Token），请求来就取令牌，有令牌就通过，没令牌就拒绝。
- **优点**：限制平均速率的同时，允许一定程度的突发流量；桶的大小决定突发程度。
- **数据结构**：令牌数量+上次补充时间。
- **场景**：互联网接口限流，允许一定突发，兼顾平均速率。

#### 3.3 限流维度与分布式实现
##### 常见限流维度
- IP地址、认证用户ID、租户、API路由、API Key、下游服务类型。

##### 本地计数器的局限
单机内存计数器只在当前实例生效，多实例部署下每个实例单独计数，总流量是单实例阈值×实例数，无法精确控制总流量；而且负载均衡不均的话更不准。

##### 分布式限流
用Redis等共享存储统一计数，所有实例共享同一个计数器，全局流量控制准确。
- 代价：增加Redis网络开销，每次请求都要查Redis；需要考虑Redis原子性、Lua脚本保证检查+扣减原子。

#### 3.4 Spring Cloud Gateway限流
官方参考：**RequestRateLimiter GatewayFilter Factory | Spring Cloud Gateway请求限流过滤器工厂**：[https://docs.spring.io/spring-cloud-gateway/reference/5.0/spring-cloud-gateway-server-webflux/gatewayfilter-factories/requestratelimiter-factory.html](https://docs.spring.io/spring-cloud-gateway/reference/5.0/spring-cloud-gateway-server-webflux/gatewayfilter-factories/requestratelimiter-factory.html)

- **RequestRateLimiter**：Gateway内置限流过滤器，在路由层面对请求限流。
- **KeyResolver**：解析限流键的接口，决定按什么限流（用户、IP、参数等）。
  
  > 安全注意：不能用未经认证的请求参数当作用户身份，容易被绕过。
- **Redis实现**：基于令牌桶算法，用Redis存储令牌状态，分布式限流。
- **核心参数**：
  - replenishRate：每秒补充多少令牌（平均速率）。
  - burstCapacity：令牌桶最大容量（突发能力）。
  - requestedTokens：每个请求消耗多少令牌。
- **触发结果**：返回`429 Too Many Requests`状态码，响应头可带`Retry-After`。
- **职责边界**：网关限流是入口层的流量防护，服务内部的业务配额还需要业务层控制。

### 模块四：接口防重放与请求认证
#### 4.1 重放攻击的基本原理
##### 什么是重放攻击
攻击者截获了一个合法的请求报文（已经正确签名），在之后的时间再次提交给服务端，利用原请求的合法身份执行操作。
- 核心：请求本身是合法的、签名是对的，只是被重复提交了。

##### 概念区分
| 概念         | 核心问题                       | 解决重点                         |
| :----------- | :----------------------------- | :------------------------------- |
| 普通重复请求 | 意外的重试、重传               | 幂等控制，保证业务不重复         |
| 恶意重放     | 截获后恶意再次提交             | 防重放，保证请求新鲜、未被使用过 |
| 身份认证     | 验证你是谁                     | 校验身份凭证                     |
| 请求签名     | 验证请求没被篡改、是合法方发的 | 校验完整性与真实性               |

> 核心结论：只验证签名不能防重放；合法的旧请求签名也是对的，但它已经被用过了。

#### 4.2 核心防重放机制
##### 1. 时间戳（Timestamp）
- 原理：请求中携带当前时间戳，服务端校验时间差在允许窗口内（比如±5分钟），超过就拒绝。
- 作用：防止很久之前的旧请求被重放。
- 局限：窗口内的重放无法防止。

##### 2. Nonce（一次性随机数）
- 原理：客户端生成唯一随机字符串，每个请求用一次；服务端记录已使用过的Nonce，相同的直接拒绝。
- 作用：保证同一个请求标识只能用一次，窗口内防重放。
- 存储：原子占位，设置TTL，过期自动清理。

##### 3. HMAC-SHA-256 消息认证码
官方参考：**Webhook Security Cheat Sheet | Webhook安全指南**：[https://cheatsheetseries.owasp.org/cheatsheets/Webhook_Security_Cheat_Sheet.html](https://cheatsheetseries.owasp.org/cheatsheets/Webhook_Security_Cheat_Sheet.html)

- 原理：客户端和服务端共享密钥，客户端把「HTTP方法+路径+时间戳+Nonce+请求体摘要」用密钥计算HMAC签名，服务端用同样的方式重算签名对比。
- 作用：验证请求完整性（没被篡改）、验证发送方身份（有密钥）。
- 核心：签名材料必须包含时间戳和Nonce，把防重放和完整性校验绑定。

##### 4. 签名规范化
客户端和服务端必须使用完全一致的签名输入规则：
- 统一的字段顺序、大小写、字符集、换行符。
- 请求体必须先做规范化处理，再算摘要。
- 任何一点不一致都会导致签名验证失败。

##### 5. 密钥保护与轮换
- 密钥不能硬编码、不能传输、不能出现在日志里。
- 定期轮换密钥，重叠期双密钥都有效，平滑切换。
- 密钥泄露立即吊销。

#### 4.3 完整防重放处理流程
```
请求到达
  ↓
格式校验 → 非法直接拒绝
  ↓
提取时间戳 → 校验时间窗口 → 超出范围拒绝
  ↓
提取Nonce → 原子检查是否已使用 → 已使用拒绝，未使用则登记
  ↓
提取签名材料 → 服务端重算HMAC → 签名不匹配拒绝
  ↓
执行业务幂等控制
  ↓
执行业务逻辑
  ↓
返回结果 + 记录审计
```

> 执行顺序说明：先做成本低的校验（格式、时间戳），再做成本高的（签名、数据库）；一般限流在最前面，然后防重放，然后幂等。

##### TLS的作用
TLS保护传输链路不被窃听、篡改，但不能防止端点、日志、代理处截获的请求被再次提交；TLS是传输层安全，防重放是应用层安全。

#### 4.4 实现边界与常见问题
1. **时间窗口大小**：太大防重放效果差，太小对时间同步要求高，容易误杀。
2. **Nonce共享问题**：分布式部署下Nonce必须存在共享存储（Redis），所有实例共用。
3. **并发Nonce竞态**：检查和插入必须原子，用SET NX，否则两个并发相同Nonce可能都通过。
4. **业务失败后的重试**：业务失败了，同一个幂等键可以重试，但必须用新的Nonce，Nonce是一次性的。
5. **密钥泄漏后的失效**：单纯防重放无法解决密钥泄漏，这时候攻击者可以伪造签名；需要配合密钥吊销、异常检测。

### 模块五：三种机制的协同设计
#### 5.1 机制职责对比
| 机制          | 解决的核心问题                 | 典型控制点                 | 层级          |
| :------------ | :----------------------------- | :------------------------- | :------------ |
| 幂等性        | 相同业务重复提交造成重复副作用 | 业务入口、数据库约束、事务 | 业务层        |
| 限流          | 请求频率/资源消耗超过允许范围  | 网关、服务、共享计数器     | 接入层/治理层 |
| 防重放        | 已截获的合法请求被再次提交     | 请求认证、时间戳、Nonce    | 安全层        |
| 数据库事务    | 本地相关数据提交的一致性       | 业务数据与幂等记录         | 数据层        |
| 下游幂等/补偿 | 跨服务副作用重复、状态不一致   | RPC、消息、外部系统        | 分布式层      |

#### 5.2 典型场景处理策略
| 场景                                  | 处理策略                                    |
| :------------------------------------ | :------------------------------------------ |
| 同一个合法请求短时间内重试            | 幂等控制，直接返回已有结果                  |
| 同一个幂等键携带不同业务参数          | 拒绝，返回幂等键冲突错误                    |
| 不同请求大量涌入造成流量突增          | 限流，429拒绝                               |
| 相同签名请求携带相同Nonce再次提交     | 防重放拒绝，Nonce已使用                     |
| 签名合法、Nonce不同，但业务幂等键相同 | 防重放通过，幂等控制拦截                    |
| 数据库已提交，但客户端没有收到响应    | 客户端重试，服务端幂等控制返回已有结果      |
| 业务事务失败，客户端随后重新提交      | 幂等记录标记失败，允许重试，新请求重新执行  |
| 本地数据库已提交，但下游调用结果未知  | 本地事务提交，下游通过幂等/补偿保证最终一致 |

#### 5.3 核心原则
- 三层是组合关系，不是替代关系：限流防洪水，防重放防伪造，幂等防重复。
- 从外到内：限流 → 防重放 → 幂等 → 业务逻辑。
- 每一层解决自己的问题，不能互相替代。

### 五、核心业务流程
1. 请求到达Controller，校验幂等键存在、格式，校验请求参数。
2. 计算请求体的SHA-256摘要。
3. 开启数据库事务。
4. 尝试插入幂等记录（状态PROCESSING）。
   - 触发唯一键冲突 → 回滚事务 → 查询已有幂等记录。
     - 状态SUCCEEDED → 返回已保存的结果。
     - 状态PROCESSING → 返回「处理中」。
     - 状态FAILED → 重新执行。
5. 插入成功 → 执行业务逻辑，创建订单。
6. 业务成功 → 更新幂等记录为SUCCEEDED，保存响应结果。
7. 提交事务。
8. 异常回滚 → 事务回滚，幂等记录不残留成功状态。

### 六、必须实现的核心规则
1. 缺少`Idempotency-Key`直接返回400错误。
2. 相同租户、相同接口、相同幂等键，不能重复创建订单。
3. 相同幂等键但请求摘要不同，返回409冲突。
4. 幂等记录与订单创建必须在同一个事务中提交/回滚。
5. 唯一键冲突后，必须在新事务中查询已有结果。
6. 并发请求下，数据库唯一约束保证只有一个能成功创建。
7. 幂等记录设置过期时间，定期清理历史数据。
