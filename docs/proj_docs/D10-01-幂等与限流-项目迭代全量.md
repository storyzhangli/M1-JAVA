# D10-01 幂等与限流 — 项目迭代全量信息与操作

> 模块：`D10\D10_IARL`（IARL = Idempotency and Rate Limiting，幂等与限流）
> 技术基线：JDK 21、Spring Boot 3.5.16、Spring Cloud 2025.0.0、Spring Cloud Alibaba 2025.0.0.0、MyBatis-Plus 3.5.17、Redisson 3.30.0
> 端口：8080；服务名：`d10-iarl`
> 本文定位：**项目迭代的全量信息与操作手册**（做了什么、文件在哪、如何构建/启停/验证）。
> 原理与算法细节见配套文档：`D10-02-幂等与令牌桶限流-技术说明与实操指南.md`。

---

## 一、迭代目标

在现有 Spring Boot MVC 业务模块（含 Redis、Redisson、MyBatis-Plus、Nacos）基础上，新增两项能力：

| 能力 | 目标 | 关键验收 |
| --- | --- | --- |
| A. 接口幂等校验 | 同一幂等键只处理一次，重复请求返回原结果 | 5 个场景全部符合预期 |
| B. Redis 令牌桶限流 | 按维度做令牌桶限流，超限返回 429 | 突发限流、429、多客户端/用户隔离 |

迭代遵循「最小变动」：不升级依赖、不改动无关业务、不调整既有接口契约；仅新增幂等/限流相关代码，并对必要的公共配置做局部扩展。

## 二、扫描结论（迭代前现状）

- `D10` 为聚合工程（`packaging=pom`），仅含一个模块 `D10_IARL`。

## 六、启停操作

### 启动

```powershell
# 方式一：cmd
D10_IARL\bin\start.bat
# 方式二：PowerShell
D10_IARL\bin\start.ps1
```

脚本行为：定位模块根目录 → 创建 `logs`（含 `gc`、`heapdump`、`app`）→ 校验 jar → 防重复启动 → 在新窗口（标题 `D10-APP`）启动，控制台输出重定向到 `logs\console.out`。

### 停止

```powershell
D10_IARL\bin\stop.bat    # 或 bin\stop.ps1
```

### 验证启动成功

- `logs\console.out` 出现：
  - `Tomcat started on port 8080`；
  - `nacos registry, DEFAULT_GROUP d10-iarl ... register finished`；
  - `Started D10App in ... seconds`。

## 七、全量验证操作

### 一键验证

```powershell
powershell -ExecutionPolicy Bypass -File D10_IARL\script\verify_demo.ps1
```

> 脚本兼容 Windows PowerShell 5.1；内部使用 `Invoke-WebRequest -UseBasicParsing` 发送 JSON，避免引号丢失与 IE 引擎交互提示。

### A. 幂等验证（5 场景）

| 场景 | 操作 | 实测结果 |
| --- | --- | --- |
| 1. 首次 K1 | `POST /idempotent/order`，头 `Idempotency-Key: K1`，订单参数 A | 200，`execNo=1`，业务执行一次 |
| 2. 相同参数、相同 K1 | 同键同参数再次提交 | 200，**订单号与 execNo 与场景1完全相同**（返回原结果，未重复执行） |
| 3. 两个请求同时用 K3 | 并发提交两个相同请求 | 一个 200（`execNo=2`），另一个返回 `code=2001`「请求正在处理中」 |
| 4. 不同参数复用 K1 | 同键但提交不同商品/数量 | `code=1001`「幂等键 K1 已被不同参数复用，拒绝处理」 |
| 5. 新键 K2 | 用新键提交 | 200，`execNo=3`，作为新请求处理 |

最终 `GET /idempotent/exec-count` 返回 `data=3`（K1、K3、K2 各一次），符合预期。

### B. 限流验证

| 场景 | 操作 | 实测结果 |
| --- | --- | --- |
| B1 IP 维度 | 对 `/ratelimit/ip` 突发 10 次 | `200,200,429×8`（2×200、8×429） |
| B2 IP 隔离 | 头 `X-Forwarded-For: 1.1.1.1` 突发 5 次 | 独立桶，`200,200,429×3` |
| B3 用户隔离 | `X-User-Id: 100` 与 `200` 各 5 次 | 两用户各自 `200,200,429×3`，互不影响 |
| B4 业务维度 | `/ratelimit/business` 突发 5 次 | 共享桶，`200,200,429×3` |
| B5 重接口 | `/ratelimit/heavy`（每次 2 令牌，桶 4）突发 4 次 | `200,200,429,429`（4 令牌只够 2 次） |

### 429 响应实测

```
HTTP/1.1 429
Retry-After: 1
Content-Type: application/json

{"code":429,"msg":"请求过于频繁，已触发限流（维度=IP, id=5.5.5.5）","data":null}
```

---

## 八、验证结论

- 幂等 5 个场景全部符合预期；业务实际执行次数 = 3，与不同幂等键数量一致。
- 限流按 IP/用户/业务维度正确生成键，突发被拦截并返回 429，不同客户端/用户限额隔离。
- 应用已注册到 Nacos，`d10-iarl` 可在服务列表中查见。
