## 一、主线一：Java并发编程（JDK21 基准）
### 1. 核心知识骨架
1. **内存模型层**：JMM Java内存模型、原子性/可见性/有序性、happens-before 六大规则、volatile 内存屏障
2. **锁与同步层**：
   - `synchronized`：锁升级路径（无锁→轻量级自适应自旋锁→重量级锁）、可重入性、内存语义
   - 无锁编程：CAS 原理、ABA 问题、原子类与 `LongAdder`、VarHandle
   - AQS 体系：`ReentrantLock`、读写锁、`Condition` 条件队列
3. **任务执行层**：
   - 线程池 7 大核心参数、任务提交流程、4 种标准拒绝策略
   - `CompletableFuture` 异步编排、任务组合、异常处理
4. **JDK21 新增重点**：虚拟线程原理、结构化并发（`StructuredTaskScope`）
5. **问题治理层**：死锁四条件、活锁、饥饿、伪共享、ThreadLocal 内存泄漏

> 关键纠正：偏向锁在 JDK 15 被正式废弃并默认关闭，JDK21 不存在偏向锁阶段，旧教程相关内容为过时知识。
> 《JEP 374 | Disable and Deprecate Biased Locking》：[https://openjdk.org/jeps/374](https://openjdk.org/jeps/374)

### 2. 面试高频核心考点
- 线程池完整执行流程？为什么生产环境禁止用 `Executors` 创建线程池？
- `synchronized` 和 `ReentrantLock` 的区别？各自适用场景？
- `volatile` 的作用是什么？为什么不能保证原子性？
- 虚拟线程和平台线程的核心区别？适合什么业务场景？
- ThreadLocal 底层原理？为什么会造成内存泄漏？

### 3. 工程落地红线
- 线程池必须使用**有界队列**，必须自定义线程名前缀，禁止无界队列与匿名线程
- `ThreadLocal` 必须配合 `try-finally` 手动调用 `remove()`，线程池复用场景必然内存泄漏
- 不要池化虚拟线程；IO 密集型场景优先虚拟线程，CPU 密集型优先平台线程池
- `CompletableFuture` 必须显式传入自定义线程池，禁止共用公共 `ForkJoinPool`
- 不要将长时间 IO 操作放在 `synchronized` 锁块中，放大锁竞争开销

## 二、主线二：Spring IoC & AOP
### 1. 核心知识骨架
1. **IoC 容器**：Bean 定义注册、实例化、属性填充、初始化、销毁全生命周期；Aware 回调、BeanPostProcessor 扩展点
2. **AOP 底层**：
   - 核心术语：切面、切点、通知、连接点、织入
   - 两种动态代理：JDK 接口代理 vs CGLIB 子类代理
   - SpringBoot 3.x 默认启用 CGLIB 类代理
3. **声明式事务**：
   - 底层链路：代理对象 → `TransactionInterceptor` → 事务管理器 → 线程绑定数据库连接
   - 7 种事务传播行为，核心 3 种：`REQUIRED` / `REQUIRES_NEW` / `NESTED`
   - 8 类事务失效场景与根因

> 官方依据：声明式事务基于 AOP 代理实现，仅外部代理调用会被事务拦截器处理。
> 《Understanding the Spring Framework’s declarative transaction implementation》：[https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-decl-explained.html](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-decl-explained.html)

### 2. 面试高频核心考点
- 简述 Spring Bean 的完整生命周期？`@PostConstruct`、`InitializingBean`、`init-method` 的执行顺序？
- JDK 动态代理和 CGLIB 的区别？SpringBoot 默认使用哪一种？
- 事务传播 `REQUIRED`、`REQUIRES_NEW`、`NESTED` 的核心区别？
- `@Transactional` 失效的常见场景？根本原因是什么？
- `BeanPostProcessor` 和 `BeanFactoryPostProcessor` 的区别？

### 3. 工程落地红线
- **同类内部调用事务必然失效**：`this` 调用绕过代理，是生产环境事务问题第一诱因
- 事务方法必须声明为 `public`，`private`、`final` 方法无法被代理拦截
- 默认仅回滚 `RuntimeException` 与 `Error`，必须统一配置 `rollbackFor = Exception.class`
- 禁止在事务方法内吞掉异常不抛出，异常无法到达事务拦截器则不会触发回滚
- `REQUIRES_NEW` 会占用独立数据库连接，高并发下可能耗尽连接池

## 三、主线三：Spring Boot 核心机制
### 1. 核心知识骨架
1. **启动注解**：`@SpringBootApplication` 三合一组合：`@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`
2. **自动配置原理**：
   - 核心驱动：`AutoConfigurationImportSelector`
   - 注册文件：`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`
   - 按需装配：`@Conditional` 系列条件注解
3. **Starter 机制**：依赖聚合 + 自动配置封装，官方命名 `spring-boot-starter-xxx`，第三方命名 `xxx-spring-boot-starter`
4. **版本断层变更**：
   - SpringBoot 3.x 废弃 `spring.factories` 自动配置注册方式
   - 全面迁移 Jakarta EE，`javax.*` 包全部替换为 `jakarta.*`
   - 原生支持虚拟线程、AOT 编译与 GraalVM 原生镜像

> 官方依据：Spring Boot 3.x 自定义自动配置需通过 `AutoConfiguration.imports` 文件注册。
> 《Creating Your Own Auto-configuration》：[https://docs.spring.io/spring-boot/reference/features/developing-auto-configuration.html](https://docs.spring.io/spring-boot/reference/features/developing-auto-configuration.html)

### 2. 面试高频核心考点
- Spring Boot 自动配置的完整执行流程？
- Starter 和自动配置的关系与区别？
- SpringBoot 3 相对 SpringBoot 2 有哪些核心破坏性变更？
- `@ConditionalOnMissingBean` 的作用和设计思想？
- 如何排查某个自动配置没有生效？

### 3. 工程落地红线
- 自定义 Starter 必须使用 `AutoConfiguration.imports` 文件，`spring.factories` 在 3.x 中自动配置不再生效
- 禁止手动 `new ObjectMapper`，优先注入 Spring 容器全局配置的实例，避免日期序列化等问题
- Jakarta 迁移后，`@PostConstruct` 等注解必须使用 `jakarta.annotation` 包，否则静默失效
- 自动配置仅提供默认兜底实现，用户自定义 Bean 优先级更高，`@ConditionalOnMissingBean` 才会生效

## 四、主线四：MySQL 核心（InnoDB 索引与优化）
### 1. 核心知识骨架
1. **索引底层**：InnoDB B+Tree 结构、聚簇索引与二级索引、回表、覆盖索引
2. **联合索引规则**：最左前缀原则、等值条件在前范围条件在后、范围列之后的列无法用于索引查找
3. **执行计划分析**：`EXPLAIN` 关键字段解读（`type` 层级、`key_len`、`rows`、`Extra`）
4. **优化体系**：慢查询定位、索引失效场景、SQL 优化方法论
5. **事务与 MVCC**：隔离级别、undo log / redo log、MVCC 实现原理

> 官方依据：多列索引可利用最左侧的连续列前缀进行查找。
> 《Multiple-Column Indexes》：[https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html)

### 2. 面试高频核心考点
- 聚簇索引和二级索引的区别？什么是回表？什么是覆盖索引？
- 最左前缀原则是什么？联合索引如何设计列顺序？
- `EXPLAIN` 的 `type` 字段有哪些常见值？性能从好到差如何排序？
- 常见的索引失效场景有哪些？
- 事务隔离级别有哪些？MVCC 是如何实现的？

### 3. 工程落地红线
- 禁止对索引列使用函数运算、左模糊 `%xxx` 查询，会导致索引失效
- 联合索引遵循「等值在前、范围在后」，范围条件之后的列无法参与索引范围查找
- `Using filesort` 不等于磁盘排序，仅表示需要额外排序处理
- 禁止业务 SQL 使用 `SELECT *`，减少回表开销，提升覆盖索引概率
- 索引不是越多越好：每个索引都会增加写入维护成本，需按真实查询模式设计

## 五、主线五：Redis 缓存 + 分布式系统与事务一致性
### 1. 核心知识骨架
1. **Redis 核心底盘**：5 大基础数据结构与底层编码、单线程命令执行+多线程 IO、RDB/AOF/混合持久化、内存淘汰策略
2. **缓存三大经典问题**：穿透、击穿、雪崩的成因与完整解决方案
3. **Redis 分布式锁**：
   - 标准实现：`SET NX PX` 原子加锁 + Lua 脚本校验令牌后原子释放
   - 三大经典问题：不可重入、锁续期、误删除
   - 高可用风险：主从异步复制可能导致锁丢失
4. **分布式理论**：CAP 定理、BASE 理论、PACELC 延伸
5. **分布式事务**：2PC/XA、TCC、SAGA、可靠消息、事务 Outbox 等 7 种方案对比与选型

> 官方依据：分布式锁需通过原子命令同时设置互斥条件与过期时间，释放时必须校验所有权。
> 《Distributed Locks with Redis》：[https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

### 2. 面试高频核心考点
- 缓存穿透、击穿、雪崩的区别？分别有哪些解决方案？
- Redis 分布式锁的实现原理？存在哪些风险？如何解决？
- 如何理解 CAP 定理？为什么说分区容错是必须的？
- 常见分布式事务方案对比？业务中如何选型？
- Redis 为什么单线程还这么快？Redis 6 多线程是怎么回事？

### 3. 工程落地红线
- 分布式锁必须同时设置**过期时间+持有者唯一令牌**，避免死锁与误删他人锁
- 布隆过滤器只能保证「不存在则一定不存在」，存在误判率，不能替代缓存
- Cache-Aside 旁路缓存模式是最终一致性，而非强一致性
- 绝大多数业务场景最终一致性足够，不要盲目追求强一致，牺牲可用性与性能
- Redis 主从异步复制存在锁丢失风险，资金、库存等关键业务不能仅依赖 Redis 分布式锁
