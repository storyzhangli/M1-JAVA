## 一、概述

本模块是七阶段学习路径中**阶段1/2「Java 工程恢复 + 并发基础」**的落点，核心验证 Spring 异步线程池（`ThreadPoolTaskExecutor`）在多线程并发下的真实运行行为。文档基于 **真实编译、真实启动、真实接口调用、真实日志** 得出验证结果，不虚构任何数据。

### 1.1 验证目标
1. 验证 `bizTaskExecutor` 线程池是否正确初始化（核心/最大/队列参数）。
2. 验证 `@Async` 异步任务是否真正由自定义线程池（`biz-async-*`）并发执行。
3. 验证线程池「核心 → 队列 → 扩容 → 拒绝策略」完整工作流程。
4. 验证 `CallerRunsPolicy` 拒绝策略（任务不丢失、回退调用线程）。
5. 验证 `CompletableFuture` 并行聚合能力。

### 2.2 线程池配置核心（AsyncThreadPoolConfig）
```java
@EnableAsync
@Bean("bizTaskExecutor")
public Executor bizTaskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    int cpuCores = Runtime.getRuntime().availableProcessors(); // 本机实测 4
    executor.setCorePoolSize(cpuCores * 2);    // = 8
    executor.setMaxPoolSize(cpuCores * 4);    // = 16
    executor.setQueueCapacity(200);           // 有界队列，防 OOM
    executor.setKeepAliveSeconds(60);
    executor.setThreadNamePrefix("biz-async-");
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    executor.setWaitForTasksToCompleteOnShutdown(true);
    executor.setAwaitTerminationSeconds(30);
    executor.initialize();
    return executor;
}
```

### 2.3 七参数与执行流程对照（面试核心）
| 参数 | 本模块值 | 含义 |
| :--- | :--- | :--- |
| corePoolSize | 8（4×2） | 常驻核心线程数 |
| maximumPoolSize | 16（4×4） | 最大线程数（核心+非核心） |
| queueCapacity | 200 | 有界阻塞队列容量 |
| keepAliveSeconds | 60 | 非核心线程空闲回收时间 |
| threadNamePrefix | biz-async- | 线程名前缀，日志/jstack 可定位 |
| rejectedExecutionHandler | CallerRunsPolicy | 拒绝策略：回退调用线程执行 |
| waitForTasksToCompleteOnShutdown | true | 优雅关闭，等待任务完成 |

**执行流程（四步走）**：新任务提交 → ①核心线程未满→新建核心线程执行；②核心线程满→入队等待（队列 200）；③队列满→扩容创建非核心线程至 max 16；④max 也满→触发拒绝策略（CallerRunsPolicy 回退给调用线程，**不丢任务**）。

### 4.2 核心验证：异步由自定义线程池并发执行（n=20）
日志中 20 个任务由 **8 个核心线程** `biz-async-1`~`biz-async-8` 并发执行，每个耗时约 300ms：
```
biz-async-1  [异步开始] task=task-0, count=1     biz-async-1  [异步结束] task=task-0, cost=301ms
biz-async-2  [异步开始] task=task-1, count=2     biz-async-2  [异步结束] task=task-1, cost=307ms
biz-async-3  [异步开始] task=task-2, count=3     biz-async-3  [异步结束] task=task-2, cost=300ms
...（8 个核心线程并行）
```
> 意义：①确认 `@Async("bizTaskExecutor")` 生效，未回退到默认 `SimpleAsyncTaskExecutor`；②确认并发度 = 核心线程数 8（= CPU 核 4 × 2）。

### 4.3 扩容验证（n=300，触发「队列满 → 扩容」）
提交 300 个任务（> 队列 200 + 核心 8），线程池从 8 扩容到 **16 个最大线程**：
```
扩容后使用线程：biz-async-1 ~ biz-async-16（共 16 个）
最大线程编号：16  ✅ 达到 maximumPoolSize
```
> 意义：完整验证「核心满 → 入队 → 队列满 → 扩容至 max」的工作流程。

### 4.4 拒绝策略验证（n=1000，CallerRunsPolicy 生效）
提交 1000 个任务（远超 max 16 + 队列 200），超出的任务由**调用线程 `http-nio-8090`** 执行，**任务不丢失**：
```
由调用线程(http-nio)执行的任务数：52
全部使用线程：biz-async-1~16 + http-nio-8090
```
> 意义：`CallerRunsPolicy` 生效，队列与线程池满载时回退给提交方线程执行，天然背压、不丢弃任务。

## 六、生产级注意事项（结合用户关注点）

1. **禁止递归重试**：若在并发逻辑中做锁获取失败重试，必须用循环 + 最大次数 + 指数退避，禁止无上限递归（易栈溢出/线程耗尽）。
2. **拒绝策略选择**：`CallerRunsPolicy` 回退调用线程可背压但不丢任务，适合本场景；`DiscardPolicy`/`DiscardOldestPolicy` 会丢任务，慎用。
3. **有界队列防 OOM**：本模块 queueCapacity=200 有界，避免无界 `LinkedBlockingQueue` 堆积导致内存溢出。
4. **@Async 失效坑**：`@Async` 方法须 public，且**不能被同类内部方法直接调用**（Spring 代理失效）；跨类调用才走代理。
5. **优雅关闭**：`waitForTasksToCompleteOnShutdown=true` + `awaitTerminationSeconds=30`，停机时等待任务完成，避免丢任务。
6. **线程数估算**：CPU 密集型 = CPU 核数；IO 密集型 = 2×CPU 核数。本模块混合负载取 2×，符合实践。

## 七、踩坑记录（err_docs）

| 现象 | 根因 | 解决 |
| :--- | :--- | :--- |
| `--spring.autoconfigure.exclude` 报 `Unrecognized option` | 参数被当成 JVM 参数 | 需放在主类名之后作为程序参数 |
| 启动报 `RedisConfig required RedisConnectionFactory` | 误排除了 Redis 自动配置 | 保留 Redis 自动配置（Lettuce 惰性连接），仅排除 DataSource/MyBatis/Redisson |
| 启动报 `AuthController required SysUserMapper` | 主启动类扫到全部 Controller，Mapper 依赖 DB | 改用独立验证入口 `@Import` 仅导入线程池三件套 |
| 端口 8081 被占用 | 残留进程 | 换端口 8090 |
