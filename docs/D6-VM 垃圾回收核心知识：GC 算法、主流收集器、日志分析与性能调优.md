## 二、GC 基础与对象存活判定

### 1. GC 的定义与核心价值

**一句话定义**：GC（Garbage Collection，垃圾回收）是JVM自动管理堆内存的机制，负责识别不再被使用的对象，回收其占用的内存空间，并在必要时整理内存布局。

**解决的问题**：

- 自动内存管理，避免手动释放的遗漏与重复释放问题
- 减少内存泄漏，提升内存利用率
- 屏蔽内存管理细节，降低开发复杂度

**基本工作流程**：标记存活对象 → 回收死亡对象内存 → 可选的内存整理

>
> 官方依据：GC是HotSpot JVM内存管理的核心组成部分，用于自动回收不再可达的对象占用的堆内存。
> 《HotSpot Virtual Machine Garbage Collection Tuning Guide, Release 21 | HotSpot 虚拟机垃圾回收调优指南（Java 21）》：[https://docs.oracle.com/en/java/javase/21/gctuning/index.html](https://docs.oracle.com/en/java/javase/21/gctuning/index.html)

### 2. 对象存活判定的两种思路

#### （1）引用计数法

- **原理**：每个对象维护一个引用计数器，被引用则+1，引用失效则-1；计数为0则判定为可回收。
- **循环引用问题**：两个对象相互引用，即使整体都不再被外部引用，计数也永远不为0，无法被回收，造成内存泄漏。
- **定位**：理论算法，**不是HotSpot JVM采用的存活判定方式**。

#### （2）可达性分析（Reachability Analysis）

- **原理**：以一系列「GC Roots」根对象为起点，沿着引用链向下搜索，能到达的对象判定为存活，不可到达的对象判定为可回收。
- **优势**：解决了循环引用问题，是当前主流JVM的标准实现。

### 3. GC Roots 的典型来源

GC Roots是对象图的起点，本身必然存活，由它们引用的对象也必然存活。

1. **虚拟机栈中引用的对象**：栈帧局部变量表中的对象引用
2. **方法区中静态变量、常量引用的对象**：类静态字段、运行时常量池中的引用
3. **本地方法栈中JNI引用的对象**
4. **活跃线程本身、系统类加载器加载的类**

### 4. 四大引用类型

| 引用类型                       | 强度 | 回收时机                                   | 典型应用场景                               |
| ------------------------------ | ---- | ------------------------------------------ | ------------------------------------------ |
| **强引用**                     | 最强 | 永远不回收，直到没有任何引用指向           | 普通`new`创建的对象，绝大多数业务对象      |
| **软引用（SoftReference）**    | 次之 | 堆内存不足、即将OOM前回收                  | 内存敏感的缓存，内存足够则保留，不足则清理 |
| **弱引用（WeakReference）**    | 更弱 | 下一次GC扫描时即回收                       | 非强绑定缓存、ThreadLocalMap的key引用      |
| **虚引用（PhantomReference）** | 最弱 | 完全不影响对象存活，仅用于跟踪对象回收事件 | 管理堆外内存、直接缓冲区释放监听           |

### 5. 核心认知误区

1. ❌ 对象不可达 = 立即被回收
✅ 不可达只是具备回收资格，实际回收由GC线程调度执行，时机不确定
2. ❌ `System.gc()` 会立刻触发Full GC
✅ 只是向JVM提出回收建议，不保证立即执行；不同收集器、不同状态下响应逻辑不同
3. ❌ 外部资源（文件、连接）会被GC自动释放
✅ GC只回收堆内对象内存，外部资源必须手动在`finally`或try-with-resources中释放

## 三、经典 GC 算法

### 1. 标记—清除算法（Mark-Sweep）

**一句话定义**：分为标记和清除两个阶段，先标记所有存活对象，再统一回收死亡对象的内存。

**工作原理**：

1. 标记阶段：从GC Roots出发，遍历所有可达对象，打上存活标记
2. 清除阶段：扫描整个堆，回收没有标记的对象占用的内存

**优缺点**：

- ✅ 实现简单，不需要移动对象，存活对象多的时候效率高
- ❌ 产生大量内存碎片，大对象可能找不到连续空间分配
- ❌ 清除阶段需要扫描整个堆，效率随堆增大而下降

**适用场景**：老年代、对象存活率高、回收频率低的场景。

### 2. 标记—复制算法（Mark-Copy）

**一句话定义**：将内存分为两块相等的区域，每次只使用一块；回收时将存活对象复制到另一块，然后清空原块。

**工作原理**：

1. 内存分为From区和To区，新对象分配在From区
2. 回收时标记存活对象，全部复制到To区，按顺序整齐排列
3. 清空整个From区，From与To角色互换

**优缺点**：

- ✅ 回收后内存连续无碎片，分配速度快
- ✅ 只扫描存活对象，对象存活率低时效率极高
- ❌ 空间利用率低，只能使用一半内存
- ❌ 存活对象多时，复制开销大

**适用场景**：新生代，绝大多数对象朝生夕死，存活率低。

### 3. 标记—整理算法（Mark-Compact）

**一句话定义**：先标记存活对象，再将所有存活对象向内存一端移动，最后清理边界外的全部内存。

**工作原理**：

1. 标记阶段：同标记-清除，标记所有存活对象
2. 整理阶段：将存活对象统一移动到堆的一端，更新所有引用地址
3. 清除边界外的所有内存

**优缺点**：

- ✅ 无内存碎片，空间利用率高
- ❌ 需要移动对象，还要更新所有引用，开销大，STW时间长

**适用场景**：老年代、对象存活率高、对内存连续性要求高的场景。

### 4. 分代收集思想（Generational Collection）

**一句话定义**：基于弱分代假说的内存组织策略，将堆按对象年龄分为不同区域，采用不同算法分别回收。

**核心依据：弱分代假说**

>
> 绝大多数对象都是朝生夕死的；存活越久的对象，越不容易死亡。

**核心概念**：

- **新生代（Young Generation）**：存放新创建的对象，回收频率高，存活率低，采用复制算法
- **老年代（Old Generation）**：存放存活时间长的对象，回收频率低，存活率高，采用标记-清除或标记-整理
- **对象晋升（Promotion）**：新生代对象熬过一定次数GC后，年龄达到阈值则晋升到老年代
- **Minor GC / Young GC**：仅回收新生代
- **Full GC / Major GC**：回收整个堆，包括新生代、老年代、元空间

**跨代引用问题**：
只回收新生代时，老年代对象可能引用新生代对象，这些引用也必须作为GC Roots，否则会错把存活对象回收。

- **记忆集（Remembered Set, RSet）**：记录老年代指向新生代的引用集合，避免全堆扫描
- **写屏障（Write Barrier）**：每次给对象字段赋值时，检查是否产生跨代引用，是则记录到记忆集

>
> 重要说明：分代是一种组织策略，不是独立算法；不同收集器的分代实现各有差异，不是所有收集器都采用连续的新生代/老年代布局。

### 5. 核心概念辨析：STW、并行、并发

| 概念                        | 定义                               | 说明                                                         |
| --------------------------- | ---------------------------------- | ------------------------------------------------------------ |
| **STW（Stop-The-World）**   | 暂停所有应用线程，仅保留GC线程运行 | 所有收集器都存在STW阶段，只是时长不同；标记、复制、整理等关键操作通常需要STW |
| **并行GC（Parallel GC）**   | GC工作由多个线程并行执行           | 执行GC时业务线程仍然暂停；缩短STW时长，但还是全程STW         |
| **并发GC（Concurrent GC）** | GC的大部分工作与业务线程同时运行   | 仅在必要的节点短暂STW，大部分时间业务正常运行；降低停顿，但消耗更多CPU和内存 |

### 6. 经典算法对比表

| 算法      | 内存碎片 | 空间利用率 | 移动对象 | 暂停时间 | 适用分代 |
| --------- | -------- | ---------- | -------- | -------- | -------- |
| 标记-清除 | 多       | 高         | 否       | 中等     | 老年代   |
| 标记-复制 | 无       | 低（50%）  | 是       | 短       | 新生代   |
| 标记-整理 | 无       | 高         | 是       | 长       | 老年代   |

## 四、Serial GC 与 Parallel GC

### 1. Serial GC

**一句话定义**：单线程执行的垃圾收集器，新生代复制算法、老年代标记-整理算法。

**核心特征**：

- 全程单线程STW，只有一个GC线程工作
- 实现简单，内存开销最小
- 启用参数：`-XX:+UseSerialGC`

**适用场景**：

- 小型应用、堆内存很小的场景
- 容器环境、CPU资源受限的场景
- 客户端程序、嵌入式应用

>
> 误区：不是多核机器就一定不用Serial GC；小堆场景下，单线程避免了线程调度开销，表现可能更好。

### 2. Parallel GC

**一句话定义**：多线程并行执行的吞吐量优先收集器，新生代复制算法、老年代标记-整理算法。

**核心特征**：

- 新生代和老年代回收都采用多线程并行执行
- 全程STW，通过多线程缩短STW总时长
- 设计目标：最大化吞吐量，降低总GC时间占比
- 启用参数：`-XX:+UseParallelGC`

**优缺点**：

- ✅ 高吞吐量，GC总开销低，适合CPU密集、批处理任务
- ❌ 暂停时间较长且不可控，堆越大暂停越长

**适用场景**：

- 批处理任务、离线计算、大数据作业
- 追求高吞吐量、对单次暂停时间不敏感的场景

### 3. 两者对比

| 维度       | Serial GC          | Parallel GC          |
| ---------- | ------------------ | -------------------- |
| GC线程数   | 单线程             | 多线程               |
| 核心目标   | 简单、低开销       | 高吞吐量             |
| 暂停时间   | 长（单线程）       | 相对短（多线程并行） |
| 内存开销   | 极低               | 中等                 |
| 适用堆规模 | 小堆               | 中大型堆             |
| 典型场景   | 小型应用、资源受限 | 批处理、高吞吐服务   |

## 五、G1 GC 原理与回收流程

>
> G1（Garbage-First）是JDK 9 ~ JDK 21的默认垃圾收集器，是服务端应用的主流选型。
> 《HotSpot Virtual Machine Garbage Collection Tuning Guide, Release 21》：[https://docs.oracle.com/en/java/javase/21/gctuning/index.html](https://docs.oracle.com/en/java/javase/21/gctuning/index.html)

### 1. 设计目标

- 可预测的停顿时间：通过`-XX:MaxGCPauseMillis`设置暂停时间软目标
- 兼顾吞吐量与延迟：在满足暂停目标的前提下尽可能提升吞吐量
- 面向大堆：支持数GB到数十GB的堆内存
- 分区化设计：将堆拆分为大量小区域，灵活选择回收范围

### 2. Region 化堆布局

G1不再采用连续的新生代/老年代划分，而是将整个堆划分为多个大小相等的**Region（区域）**，每个Region大小为1~32MB，总数约2048个。

- 逻辑分代：每个Region可以动态扮演Eden、Survivor、Old、Humongous四种角色
- 新生代：一组Eden Region + 一组Survivor Region
- 老年代：大量Old Region
- 大对象区：Humongous Region，存放超过Region大小50%的大对象

### 3. 核心机制

- **CSet（Collection Set，收集集合）**：每次GC选择回收的Region集合，优先选择垃圾最多的Region
- **RSet（Remembered Set，记忆集）**：每个Region维护自己的记忆集，记录其他Region指向本Region的引用；用于避免全堆扫描
- **写屏障**：每次对象赋值时触发，更新跨Region引用的记忆集记录

### 4. 三种 GC 类型

| GC类型       | 回收范围                              | 触发条件                                     | 特点                                                         |
| ------------ | ------------------------------------- | -------------------------------------------- | ------------------------------------------------------------ |
| **Young GC** | 所有Eden + Survivor Region            | Eden区满，无法分配新对象                     | 复制算法，存活对象复制到另一个Survivor或晋升到老年代；STW    |
| **Mixed GC** | 所有新生代 + 部分垃圾多的老年代Region | 老年代占用达到阈值（默认45%）                | 混合回收，是G1的核心回收方式；包含并发标记阶段 + STW疏散阶段 |
| **Full GC**  | 整个堆                                | Mixed GC回收速度跟不上分配速度、疏散空间不足 | 单线程标记-整理，STW时间很长，应极力避免                     |

### 5. Mixed GC 完整工作流程

1. **初始标记（STW）**：标记GC Roots直接引用的对象，速度很快
2. **并发标记**：与业务线程并发，沿着引用链遍历标记所有存活对象
3. **最终标记（STW）**：修正并发标记期间的变动，完成存活对象标记
4. **筛选回收**：选择垃圾最多的Region组成CSet
5. **复制疏散（STW）**：将存活对象复制到空Region，清空回收的Region

### 6. 大对象处理

- 大小超过Region容量50%的对象判定为大对象（Humongous Object）
- 直接分配在Humongous Region，不进入新生代
- 大对象回收在Mixed GC或Full GC时处理，回收成本较高

### 7. 关键参数与特性

- `-XX:MaxGCPauseMillis`：暂停时间软目标，默认200ms；JVM尽力达成，但不保证每次都满足
- `-XX:G1HeapRegionSize`：设置单个Region大小，1~32MB，2的幂
- 自适应行为：根据历史GC数据动态调整新生代大小、回收Region数量，尽量达成暂停目标

### 8. 常见风险

- **To-space exhausted**：疏散时没有足够的空Region存放存活对象，触发Full GC
- **连续Full GC**：大对象过多、堆内存不足、存活集过大都可能导致
- 软目标不等于硬承诺：堆过大、存活对象过多时，暂停时间可能超出目标

## 六、ZGC 原理与版本差异

### 1. 设计目标

ZGC（Z Garbage Collector）是低延迟垃圾收集器，目标是在TB级堆下，GC暂停时间保持在亚毫秒级，几乎不随堆大小增长。

>
> 官方依据：JEP 377将ZGC转正为生产特性，核心目标是可伸缩的低延迟GC。
> 《JEP 377: ZGC: A Scalable Low-Latency Garbage Collector (Production)》：[https://openjdk.org/jeps/377](https://openjdk.org/jeps/377)

### 2. 核心技术原理

- **着色指针（Colored Pointers）**：对象指针中嵌入元数据位，标记对象的存活、重定位状态
- **负载屏障（Load Barrier）**：读取对象引用时触发，检查指针元数据，必要时处理对象重定位
- **存储屏障（Store Barrier）**：写入对象引用时触发，维护跨代/跨区域引用记录

**核心特点**：

- 绝大多数标记、重定位工作都与业务线程并发执行
- 仅在标记开始/结束、重定位开始/结束有极短STW
- 支持8MB~16TB堆内存，暂停时间普遍<1ms

### 3. JDK 21 分代 ZGC（Generational ZGC）

JDK 21引入分代模式的ZGC，进一步优化性能，降低内存开销。

>
> 官方依据：JEP 439为JDK21新增分代ZGC能力，将对象分为年轻代和老年代分别回收。
> 《JEP 439: Generational ZGC》：[https://openjdk.org/jeps/439](https://openjdk.org/jeps/439)

**核心变化**：

- 逻辑分为年轻代和老年代，年轻代回收更频繁
- 引入存储屏障，维护老到年轻代的引用记录
- 降低GC CPU开销，减少内存碎片，提升吞吐量
- 启用参数：`-XX:+UseZGC -XX:+ZGenerational`

### 4. ZGC 与 G1 核心对比

| 维度       | G1 GC                    | ZGC                                  |
| ---------- | ------------------------ | ------------------------------------ |
| 设计目标   | 暂停时间软目标，兼顾吞吐 | 极低延迟，亚毫秒级暂停               |
| 堆布局     | Region分区，逻辑分代     | 不分代/分代两种模式，着色指针        |
| 暂停时间   | 毫秒级，软目标           | 亚毫秒级，几乎不随堆增长             |
| 吞吐量     | 高                       | 略低于G1，并发GC消耗更多CPU          |
| 内存开销   | 中等                     | 较高，需要更多内存余量               |
| 适用堆规模 | 数GB~数十GB              | 数百MB~16TB                          |
| 典型场景   | 常规Web服务、通用后端    | 低延迟在线服务、大堆应用、AI推理服务 |

### 5. 常见误区

1. ❌ ZGC完全没有STW
✅ 标记开始、重定位等节点仍有短暂STW，只是时间极短（微秒级）
2. ❌ ZGC在所有场景都比G1好
✅ 低延迟优势明显，但吞吐量略低、CPU消耗更高、内存要求更高；小堆场景优势不明显
3. ❌ JDK21默认启用ZGC
✅ JDK21默认收集器仍是G1，ZGC需要手动通过`-XX:+UseZGC`启用

## 七、CMS、Shenandoah、Epsilon 及历史版本辨析

### 1. CMS 收集器

- **全称**：Concurrent Mark Sweep，并发标记清除收集器
- **定位**：历史上著名的低延迟老年代收集器，新生代配合ParNew
- **核心问题**：内存碎片严重，长时间运行后触发Full GC；浮动垃圾；CPU占用高
- **版本状态**：JDK 9废弃，JDK 14正式移除；JDK 21完全不支持> 
> 官方依据：JEP 363正式移除CMS垃圾收集器。
> 《JEP 363: Remove the Concurrent Mark Sweep (CMS) Garbage Collector》：[https://openjdk.org/jeps/363](https://openjdk.org/jeps/363)

### 2. Shenandoah GC

- **定位**：低延迟收集器，由RedHat贡献
- **特点**：并发整理，暂停时间极低；通过Brooks指针实现并发访问
- **版本边界**：部分JDK发行版包含，OpenJDK默认构建通常包含；Oracle JDK部分版本不默认提供
- **适用**：极低延迟需求，且对应JDK发行版支持的场景

### 3. Epsilon GC

- **定位**：无操作垃圾收集器，不执行任何实际回收
- **作用**：仅负责分配内存，不回收；GC开销为0
- **适用场景**：性能测试、微基准测试、短生命周期应用；内存泄漏复现
- **注意**：绝对不能用于生产环境，会很快OOM

### 4. JDK 版本收集器演进表

| JDK版本 | 默认收集器  | 核心变化                            |
| ------- | ----------- | ----------------------------------- |
| JDK 8   | Parallel GC | CMS作为可选，永久代方法区实现       |
| JDK 9   | G1 GC       | G1成为默认，CMS废弃                 |
| JDK 11  | G1 GC       | ZGC实验性引入，元空间全面替代永久代 |
| JDK 14  | G1 GC       | 正式移除CMS                         |
| JDK 15  | G1 GC       | ZGC转正为生产特性                   |
| JDK 17  | G1 GC       | ZGC稳定性增强                       |
| JDK 21  | G1 GC       | 分代ZGC生产就绪，性能大幅提升       |

## 八、主流收集器对比与工程选型

### 1. 主流收集器多维度对比

| 维度           | Serial GC      | Parallel GC         | G1 GC                 | ZGC（分代）              |
| -------------- | -------------- | ------------------- | --------------------- | ------------------------ |
| **核心目标**   | 低开销、简单   | 最高吞吐量          | 平衡吞吐与延迟        | 极低延迟                 |
| **暂停特征**   | 全程STW，长    | 全程STW，多线程缩短 | 多阶段STW，软目标     | 极短STW，微秒级          |
| **吞吐量**     | 低             | 最高                | 高                    | 较高                     |
| **CPU消耗**    | 低             | 中                  | 中高                  | 高                       |
| **内存开销**   | 极低           | 低                  | 中等                  | 较高                     |
| **推荐堆大小** | <1GB           | 2GB~8GB             | 4GB~32GB              | 8GB~16TB                 |
| **典型场景**   | 小程序、嵌入式 | 批处理、离线计算    | 常规Web服务、通用后端 | 低延迟服务、大堆、AI服务 |

### 2. 业务场景选型建议

1. **小型应用/客户端程序**：优先Serial GC，简单稳定开销小
2. **批处理/高吞吐任务**：优先Parallel GC，最大化吞吐量
3. **常规后端Web服务**：优先G1 GC，平衡吞吐与延迟，通用性最强
4. **低延迟在线服务/大堆应用**：优先ZGC，对延迟要求高、堆大、CPU资源充足
5. **AI推理/大模型服务**：优先ZGC，大堆、低停顿，避免GC影响推理延迟

### 3. 选型原则

- 没有万能收集器，必须结合业务目标、堆大小、CPU资源选择
- 优先默认值：无明确需求时优先使用JDK默认的G1
- 先压测再选型：必须基于真实业务压测数据对比，不能仅凭理论选择

## 十、GC 常见故障与诊断流程

### 1. 常见故障场景分析

| 故障现象                 | 可能原因                                       | 排查方向                               |
| ------------------------ | ---------------------------------------------- | -------------------------------------- |
| **Young GC过于频繁**     | 新生代太小、对象分配速率过高、存活对象太多     | 看Eden大小、分配速率、晋升年龄         |
| **Full GC频繁**          | 老年代满、大对象过多、元空间满、内存泄漏       | 看老年代占用、大对象数量、元空间使用率 |
| **GC暂停时间过长**       | 存活对象太多、大对象、引用链复杂、GC线程数不足 | 看存活集大小、Region大小、暂停日志     |
| **堆使用率持续上升**     | 内存泄漏、业务量增长、缓存未过期               | 堆转储分析对象引用链、增长趋势         |
| **GC后存活占比仍很高**   | 长生命周期对象过多、静态集合持有、内存泄漏     | 类直方图、堆转储找大对象               |
| **OOM：Java heap space** | 堆太小、内存泄漏、大对象集中创建               | 保留堆转储，分析泄漏点                 |

### 2. 结构化诊断流程

1. **收集现象**：异常信息、响应时间、吞吐量、CPU、内存、发生时间与频率
2. **确认环境**：JDK版本、收集器类型、JVM参数、容器内存限制
3. **采集证据**：GC日志、jstat趋势、堆转储、JFR记录、业务代码变更
4. **建立假设**：至少列出2~3个可能原因，不直接下定论
5. **验证假设**：通过日志、堆转储、代码分析逐一验证排除
6. **制定方案**：优先修复代码/配置问题，最后调整堆大小与收集器
7. **对照验证**：相同负载下对比调整前后指标
8. **记录结论**：根因、证据、修复措施、验证结果、残余风险

### 3. 核心避坑

- ❌ 只看一条日志就下结论
- ❌ 遇到OOM直接加堆内存
- ❌ 频繁Full GC就换收集器
- ✅ 先排除代码问题、内存泄漏，再调JVM参数

## 十一、GC 参数与调优方法

### 1. 核心参数汇总表

| 参数                              | 作用              | 适用收集器 |
| --------------------------------- | ----------------- | ---------- |
| `-Xms`                            | 初始堆大小        | 通用       |
| `-Xmx`                            | 最大堆大小        | 通用       |
| `-Xmn`                            | 新生代大小        | 分代收集器 |
| `-XX:+UseSerialGC`                | 启用Serial GC     | 通用       |
| `-XX:+UseParallelGC`              | 启用Parallel GC   | 通用       |
| `-XX:+UseG1GC`                    | 启用G1 GC         | 通用       |
| `-XX:+UseZGC`                     | 启用ZGC           | 通用       |
| `-XX:+ZGenerational`              | 启用分代ZGC       | ZGC        |
| `-XX:MaxGCPauseMillis`            | 最大暂停软目标    | G1/ZGC     |
| `-XX:G1HeapRegionSize`            | G1单个Region大小  | G1         |
| `-XX:+HeapDumpOnOutOfMemoryError` | OOM自动生成堆转储 | 通用       |
| `-Xlog:gc*`                       | 开启GC详细日志    | 通用       |

### 2. 调优核心原则

1. **先测量，再调整**：没有数据不调参，先采集基线再优化
2. **优先业务优化**：先优化代码、对象生命周期、缓存策略，再调JVM
3. **一次只改一个参数**：避免多变量混淆，无法归因效果
4. **压测验证**：必须用真实业务压测验证调优效果
5. **避免过度调优**：满足业务目标即可，追求极致收益递减

### 3. 常见调优误区

- ❌ 堆越大越好：堆越大Full GC暂停越长，够用即可
- ❌ 新生代越大越好：新生代大会减少Young GC频率，但增加单次回收时间
- ❌ 暂停时间越短越好：低延迟通常牺牲吞吐量和CPU
- ❌ 频繁GC就是有问题：高分配速率下GC频繁是正常的，看吞吐量和总耗时

### 实验 1：对象分配与年轻代回收

import java.util.ArrayList;
import java.util.List;

public class YoungGcDemo {
    public static void main(String[] args) {
        List<byte[]> list = new ArrayList<>();
        for (int i = 0; i < 1000; i++) {
            // 每次分配1MB，总共约1GB
            list.add(new byte[1024 * 1024]);
        }
        // 保持引用，避免立即回收
        System.out.println("分配完成，列表大小: " + list.size());
    }
}
```

**运行命令**：

```
java -Xms256m -Xmx256m -Xlog:gc*,gc+heap=info YoungGcDemo

**预期观察**：

- 多次Young GC，Eden满触发
- 每次GC后存活对象晋升到老年代

**说明**：

- 堆越小，Young GC越频繁

### 实验 5：GC 问题诊断报告（模板）

**报告结构**：

1. **问题现象**：服务响应超时，监控显示Full GC每10分钟一次，堆使用率90%+
2. **环境信息**：JDK21、G1、-Xms4g -Xmx4g、业务为订单查询服务
3. **证据收集**：
   - GC日志：老年代回收后占比仍85%，存活对象持续增长
   - jmap直方图：`OrderVO`对象数量异常高
   - 代码排查：本地缓存未设置过期时间
4. **根因定位**：本地缓存无限增长，导致老年代对象过多，频繁Full GC
5. **修复方案**：缓存增加过期时间、最大容量限制；改用Redis分布式缓存
6. **验证结果**：Full GC消失，老年代稳定在40%左右
7. **残余风险**：缓存命中率略有下降，需业务评估可接受

## 十三、面试高频问题与参考答案

### 1. 简单说一下GC的可达性分析？

从GC Roots根对象出发，沿着引用链遍历，能到达的对象标记为存活，不可到达的判定为可回收。解决了引用计数法的循环引用问题，是HotSpot的标准实现。GC Roots主要包括栈局部变量、静态变量、JNI引用等。

### 2. 标记清除、标记复制、标记整理的区别？

- 标记清除：标记存活，直接回收死亡对象；快但碎片多
- 标记复制：分两块，存活对象复制到另一块；无碎片但空间利用率低，适合新生代
- 标记整理：标记后移动存活对象到一端；无碎片空间利用率高，但移动对象开销大，适合老年代

### 3. 分代收集的依据是什么？

基于弱分代假说：绝大多数对象朝生夕死，存活越久越不容易死。所以分成新生代和老年代，新生代用复制算法高频回收，老年代用标记整理低频回收，兼顾效率与开销。

### 4. G1的工作原理？和CMS有什么区别？

G1将堆分成多个Region，每个Region可扮演Eden、Survivor、Old角色。每次优先回收垃圾最多的Region，通过记忆集记录跨区引用。分为Young GC、Mixed GC、Full GC三种。
和CMS比：G1是整理算法，碎片少；可预测暂停时间；不只是老年代，整堆都回收；没有CMS的浮动垃圾和严重碎片问题。

### 5. ZGC为什么这么快？低延迟怎么实现的？

核心是着色指针技术，把对象状态信息存在指针的元数据位里。然后通过负载屏障，读对象的时候处理重定位。大部分标记、重定位工作都和业务线程并发，只有开始结束极短停顿，所以暂停时间在亚毫秒级。

### 6. 什么是STW？所有GC都有STW吗？

STW就是暂停所有应用线程，只跑GC线程。所有GC都有STW阶段，只是时长不同。哪怕ZGC也有标记开始、重定位节点的短暂STW，不是完全没有。

### 7. 什么情况会触发Full GC？怎么避免？

G1中：大对象过多、Mixed GC赶不上分配速度、疏散空间不足、元空间满。
避免：调大堆、减少大对象、优化对象生命周期、调大并发标记线程数。

### 8. 内存泄漏怎么排查？

1. 先看GC日志：老年代占用是不是持续上涨，GC后不下降
2. 导堆转储，用MAT/JProfiler分析大对象、引用链
3. 找长生命周期集合、静态变量、缓存、监听器持有
4. 结合代码定位泄漏点，修复引用释放逻辑

### 9. 怎么选择垃圾收集器？

- 小堆小程序用Serial
- 批处理高吞吐用Parallel
- 通用服务默认G1，平衡最好
- 低延迟大堆用ZGC
- 最终要靠真实压测数据决定，不能只看理论

### 10. System.gc() 有什么用？会立刻执行吗？

只是建议JVM执行GC，不保证立刻执行。一般用在堆转储前、闲时主动回收、测试场景。生产环境通常建议禁用显式GC调用，避免不必要的Full GC。

## 二、GC 基础与对象存活判定

### 1. GC 的定义与核心价值

**一句话定义**：GC（Garbage Collection，垃圾回收）是JVM自动管理堆内存的机制，负责识别不再被使用的对象，回收其占用的内存空间，并在必要时整理内存布局。

**解决的问题**：

- 自动内存管理，避免手动释放的遗漏与重复释放问题
- 减少内存泄漏，提升内存利用率
- 屏蔽内存管理细节，降低开发复杂度

**基本工作流程**：标记存活对象 → 回收死亡对象内存 → 可选的内存整理

> 官方依据：GC是HotSpot JVM内存管理的核心组成部分，用于自动回收不再可达的对象占用的堆内存。 《HotSpot Virtual Machine Garbage Collection Tuning Guide, Release 21 | HotSpot 虚拟机垃圾回收调优指南（Java 21）》：https://docs.oracle.com/en/java/javase/21/gctuning/index.html

### 2. 对象存活判定的两种思路

#### （1）引用计数法

- **原理**：每个对象维护一个引用计数器，被引用则+1，引用失效则-1；计数为0则判定为可回收。
- **循环引用问题**：两个对象相互引用，即使整体都不再被外部引用，计数也永远不为0，无法被回收，造成内存泄漏。
- **定位**：理论算法，**不是HotSpot JVM采用的存活判定方式**。

#### （2）可达性分析（Reachability Analysis）

- **原理**：以一系列「GC Roots」根对象为起点，沿着引用链向下搜索，能到达的对象判定为存活，不可到达的对象判定为可回收。
- **优势**：解决了循环引用问题，是当前主流JVM的标准实现。

### 3. GC Roots 的典型来源

GC Roots是对象图的起点，本身必然存活，由它们引用的对象也必然存活。

1. **虚拟机栈中引用的对象**：栈帧局部变量表中的对象引用
2. **方法区中静态变量、常量引用的对象**：类静态字段、运行时常量池中的引用
3. **本地方法栈中JNI引用的对象**
4. **活跃线程本身、系统类加载器加载的类**

### 4. 四大引用类型

| 引用类型                       | 强度 | 回收时机                                   | 典型应用场景                               |
| ------------------------------ | ---- | ------------------------------------------ | ------------------------------------------ |
| **强引用**                     | 最强 | 永远不回收，直到没有任何引用指向           | 普通`new`创建的对象，绝大多数业务对象      |
| **软引用（SoftReference）**    | 次之 | 堆内存不足、即将OOM前回收                  | 内存敏感的缓存，内存足够则保留，不足则清理 |
| **弱引用（WeakReference）**    | 更弱 | 下一次GC扫描时即回收                       | 非强绑定缓存、ThreadLocalMap的key引用      |
| **虚引用（PhantomReference）** | 最弱 | 完全不影响对象存活，仅用于跟踪对象回收事件 | 管理堆外内存、直接缓冲区释放监听           |

### 5. 核心认知误区

1. ❌ 对象不可达 = 立即被回收 ✅ 不可达只是具备回收资格，实际回收由GC线程调度执行，时机不确定
2. ❌ `System.gc()` 会立刻触发Full GC ✅ 只是向JVM提出回收建议，不保证立即执行；不同收集器、不同状态下响应逻辑不同
3. ❌ 外部资源（文件、连接）会被GC自动释放 ✅ GC只回收堆内对象内存，外部资源必须手动在`finally`或try-with-resources中释放

## 三、经典 GC 算法

### 1. 标记—清除算法（Mark-Sweep）

**一句话定义**：分为标记和清除两个阶段，先标记所有存活对象，再统一回收死亡对象的内存。

**工作原理**：

1. 标记阶段：从GC Roots出发，遍历所有可达对象，打上存活标记
2. 清除阶段：扫描整个堆，回收没有标记的对象占用的内存

**优缺点**：

- ✅ 实现简单，不需要移动对象，存活对象多的时候效率高
- ❌ 产生大量内存碎片，大对象可能找不到连续空间分配
- ❌ 清除阶段需要扫描整个堆，效率随堆增大而下降

**适用场景**：老年代、对象存活率高、回收频率低的场景。

### 2. 标记—复制算法（Mark-Copy）

**一句话定义**：将内存分为两块相等的区域，每次只使用一块；回收时将存活对象复制到另一块，然后清空原块。

**工作原理**：

1. 内存分为From区和To区，新对象分配在From区
2. 回收时标记存活对象，全部复制到To区，按顺序整齐排列
3. 清空整个From区，From与To角色互换

**优缺点**：

- ✅ 回收后内存连续无碎片，分配速度快
- ✅ 只扫描存活对象，对象存活率低时效率极高
- ❌ 空间利用率低，只能使用一半内存
- ❌ 存活对象多时，复制开销大

**适用场景**：新生代，绝大多数对象朝生夕死，存活率低。

### 3. 标记—整理算法（Mark-Compact）

**一句话定义**：先标记存活对象，再将所有存活对象向内存一端移动，最后清理边界外的全部内存。

**工作原理**：

1. 标记阶段：同标记-清除，标记所有存活对象
2. 整理阶段：将存活对象统一移动到堆的一端，更新所有引用地址
3. 清除边界外的所有内存

**优缺点**：

- ✅ 无内存碎片，空间利用率高
- ❌ 需要移动对象，还要更新所有引用，开销大，STW时间长

**适用场景**：老年代、对象存活率高、对内存连续性要求高的场景。

### 4. 分代收集思想（Generational Collection）

**一句话定义**：基于弱分代假说的内存组织策略，将堆按对象年龄分为不同区域，采用不同算法分别回收。

**核心依据：弱分代假说**

> 绝大多数对象都是朝生夕死的；存活越久的对象，越不容易死亡。

**核心概念**：

- **新生代（Young Generation）**：存放新创建的对象，回收频率高，存活率低，采用复制算法
- **老年代（Old Generation）**：存放存活时间长的对象，回收频率低，存活率高，采用标记-清除或标记-整理
- **对象晋升（Promotion）**：新生代对象熬过一定次数GC后，年龄达到阈值则晋升到老年代
- **Minor GC / Young GC**：仅回收新生代
- **Full GC / Major GC**：回收整个堆，包括新生代、老年代、元空间

**跨代引用问题**： 只回收新生代时，老年代对象可能引用新生代对象，这些引用也必须作为GC Roots，否则会错把存活对象回收。

- **记忆集（Remembered Set, RSet）**：记录老年代指向新生代的引用集合，避免全堆扫描
- **写屏障（Write Barrier）**：每次给对象字段赋值时，检查是否产生跨代引用，是则记录到记忆集

> 重要说明：分代是一种组织策略，不是独立算法；不同收集器的分代实现各有差异，不是所有收集器都采用连续的新生代/老年代布局。

### 5. 核心概念辨析：STW、并行、并发

| 概念                        | 定义                               | 说明                                                         |
| --------------------------- | ---------------------------------- | ------------------------------------------------------------ |
| **STW（Stop-The-World）**   | 暂停所有应用线程，仅保留GC线程运行 | 所有收集器都存在STW阶段，只是时长不同；标记、复制、整理等关键操作通常需要STW |
| **并行GC（Parallel GC）**   | GC工作由多个线程并行执行           | 执行GC时业务线程仍然暂停；缩短STW时长，但还是全程STW         |
| **并发GC（Concurrent GC）** | GC的大部分工作与业务线程同时运行   | 仅在必要的节点短暂STW，大部分时间业务正常运行；降低停顿，但消耗更多CPU和内存 |

### 6. 经典算法对比表

| 算法      | 内存碎片 | 空间利用率 | 移动对象 | 暂停时间 | 适用分代 |
| --------- | -------- | ---------- | -------- | -------- | -------- |
| 标记-清除 | 多       | 高         | 否       | 中等     | 老年代   |
| 标记-复制 | 无       | 低（50%）  | 是       | 短       | 新生代   |
| 标记-整理 | 无       | 高         | 是       | 长       | 老年代   |

## 四、Serial GC 与 Parallel GC

### 1. Serial GC

**一句话定义**：单线程执行的垃圾收集器，新生代复制算法、老年代标记-整理算法。

**核心特征**：

- 全程单线程STW，只有一个GC线程工作
- 实现简单，内存开销最小
- 启用参数：`-XX:+UseSerialGC`

**适用场景**：

- 小型应用、堆内存很小的场景
- 容器环境、CPU资源受限的场景
- 客户端程序、嵌入式应用

> 误区：不是多核机器就一定不用Serial GC；小堆场景下，单线程避免了线程调度开销，表现可能更好。

### 2. Parallel GC

**一句话定义**：多线程并行执行的吞吐量优先收集器，新生代复制算法、老年代标记-整理算法。

**核心特征**：

- 新生代和老年代回收都采用多线程并行执行
- 全程STW，通过多线程缩短STW总时长
- 设计目标：最大化吞吐量，降低总GC时间占比
- 启用参数：`-XX:+UseParallelGC`

**优缺点**：

- ✅ 高吞吐量，GC总开销低，适合CPU密集、批处理任务
- ❌ 暂停时间较长且不可控，堆越大暂停越长

**适用场景**：

- 批处理任务、离线计算、大数据作业
- 追求高吞吐量、对单次暂停时间不敏感的场景

### 3. 两者对比

| 维度       | Serial GC          | Parallel GC          |
| ---------- | ------------------ | -------------------- |
| GC线程数   | 单线程             | 多线程               |
| 核心目标   | 简单、低开销       | 高吞吐量             |
| 暂停时间   | 长（单线程）       | 相对短（多线程并行） |
| 内存开销   | 极低               | 中等                 |
| 适用堆规模 | 小堆               | 中大型堆             |
| 典型场景   | 小型应用、资源受限 | 批处理、高吞吐服务   |

## 五、G1 GC 原理与回收流程

> G1（Garbage-First）是JDK 9 ~ JDK 21的默认垃圾收集器，是服务端应用的主流选型。 《HotSpot Virtual Machine Garbage Collection Tuning Guide, Release 21》：https://docs.oracle.com/en/java/javase/21/gctuning/index.html

### 1. 设计目标

- 可预测的停顿时间：通过`-XX:MaxGCPauseMillis`设置暂停时间软目标
- 兼顾吞吐量与延迟：在满足暂停目标的前提下尽可能提升吞吐量
- 面向大堆：支持数GB到数十GB的堆内存
- 分区化设计：将堆拆分为大量小区域，灵活选择回收范围

### 2. Region 化堆布局

G1不再采用连续的新生代/老年代划分，而是将整个堆划分为多个大小相等的**Region（区域）**，每个Region大小为1~32MB，总数约2048个。

- 逻辑分代：每个Region可以动态扮演Eden、Survivor、Old、Humongous四种角色
- 新生代：一组Eden Region + 一组Survivor Region
- 老年代：大量Old Region
- 大对象区：Humongous Region，存放超过Region大小50%的大对象

### 3. 核心机制

- **CSet（Collection Set，收集集合）**：每次GC选择回收的Region集合，优先选择垃圾最多的Region
- **RSet（Remembered Set，记忆集）**：每个Region维护自己的记忆集，记录其他Region指向本Region的引用；用于避免全堆扫描
- **写屏障**：每次对象赋值时触发，更新跨Region引用的记忆集记录

### 4. 三种 GC 类型

| GC类型       | 回收范围                              | 触发条件                                     | 特点                                                         |
| ------------ | ------------------------------------- | -------------------------------------------- | ------------------------------------------------------------ |
| **Young GC** | 所有Eden + Survivor Region            | Eden区满，无法分配新对象                     | 复制算法，存活对象复制到另一个Survivor或晋升到老年代；STW    |
| **Mixed GC** | 所有新生代 + 部分垃圾多的老年代Region | 老年代占用达到阈值（默认45%）                | 混合回收，是G1的核心回收方式；包含并发标记阶段 + STW疏散阶段 |
| **Full GC**  | 整个堆                                | Mixed GC回收速度跟不上分配速度、疏散空间不足 | 单线程标记-整理，STW时间很长，应极力避免                     |

### 5. Mixed GC 完整工作流程

1. **初始标记（STW）**：标记GC Roots直接引用的对象，速度很快
2. **并发标记**：与业务线程并发，沿着引用链遍历标记所有存活对象
3. **最终标记（STW）**：修正并发标记期间的变动，完成存活对象标记
4. **筛选回收**：选择垃圾最多的Region组成CSet
5. **复制疏散（STW）**：将存活对象复制到空Region，清空回收的Region

### 6. 大对象处理

- 大小超过Region容量50%的对象判定为大对象（Humongous Object）
- 直接分配在Humongous Region，不进入新生代
- 大对象回收在Mixed GC或Full GC时处理，回收成本较高

### 7. 关键参数与特性

- `-XX:MaxGCPauseMillis`：暂停时间软目标，默认200ms；JVM尽力达成，但不保证每次都满足
- `-XX:G1HeapRegionSize`：设置单个Region大小，1~32MB，2的幂
- 自适应行为：根据历史GC数据动态调整新生代大小、回收Region数量，尽量达成暂停目标

### 8. 常见风险

- **To-space exhausted**：疏散时没有足够的空Region存放存活对象，触发Full GC
- **连续Full GC**：大对象过多、堆内存不足、存活集过大都可能导致
- 软目标不等于硬承诺：堆过大、存活对象过多时，暂停时间可能超出目标

## 六、ZGC 原理与版本差异

### 1. 设计目标

ZGC（Z Garbage Collector）是低延迟垃圾收集器，目标是在TB级堆下，GC暂停时间保持在亚毫秒级，几乎不随堆大小增长。

> 官方依据：JEP 377将ZGC转正为生产特性，核心目标是可伸缩的低延迟GC。 《JEP 377: ZGC: A Scalable Low-Latency Garbage Collector (Production)》：https://openjdk.org/jeps/377

### 2. 核心技术原理

- **着色指针（Colored Pointers）**：对象指针中嵌入元数据位，标记对象的存活、重定位状态
- **负载屏障（Load Barrier）**：读取对象引用时触发，检查指针元数据，必要时处理对象重定位
- **存储屏障（Store Barrier）**：写入对象引用时触发，维护跨代/跨区域引用记录

**核心特点**：

- 绝大多数标记、重定位工作都与业务线程并发执行
- 仅在标记开始/结束、重定位开始/结束有极短STW
- 支持8MB~16TB堆内存，暂停时间普遍<1ms

### 3. JDK 21 分代 ZGC（Generational ZGC）

JDK 21引入分代模式的ZGC，进一步优化性能，降低内存开销。

> 官方依据：JEP 439为JDK21新增分代ZGC能力，将对象分为年轻代和老年代分别回收。 《JEP 439: Generational ZGC》：https://openjdk.org/jeps/439

**核心变化**：

- 逻辑分为年轻代和老年代，年轻代回收更频繁
- 引入存储屏障，维护老到年轻代的引用记录
- 降低GC CPU开销，减少内存碎片，提升吞吐量
- 启用参数：`-XX:+UseZGC -XX:+ZGenerational`

### 4. ZGC 与 G1 核心对比

| 维度       | G1 GC                    | ZGC                                  |
| ---------- | ------------------------ | ------------------------------------ |
| 设计目标   | 暂停时间软目标，兼顾吞吐 | 极低延迟，亚毫秒级暂停               |
| 堆布局     | Region分区，逻辑分代     | 不分代/分代两种模式，着色指针        |
| 暂停时间   | 毫秒级，软目标           | 亚毫秒级，几乎不随堆增长             |
| 吞吐量     | 高                       | 略低于G1，并发GC消耗更多CPU          |
| 内存开销   | 中等                     | 较高，需要更多内存余量               |
| 适用堆规模 | 数GB~数十GB              | 数百MB~16TB                          |
| 典型场景   | 常规Web服务、通用后端    | 低延迟在线服务、大堆应用、AI推理服务 |

### 5. 常见误区

1. ❌ ZGC完全没有STW ✅ 标记开始、重定位等节点仍有短暂STW，只是时间极短（微秒级）
2. ❌ ZGC在所有场景都比G1好 ✅ 低延迟优势明显，但吞吐量略低、CPU消耗更高、内存要求更高；小堆场景优势不明显
3. ❌ JDK21默认启用ZGC ✅ JDK21默认收集器仍是G1，ZGC需要手动通过`-XX:+UseZGC`启用

## 七、CMS、Shenandoah、Epsilon 及历史版本辨析

### 1. CMS 收集器

- **全称**：Concurrent Mark Sweep，并发标记清除收集器

- **定位**：历史上著名的低延迟老年代收集器，新生代配合ParNew

- **核心问题**：内存碎片严重，长时间运行后触发Full GC；浮动垃圾；CPU占用高

- 版本状态

  ：JDK 9废弃，JDK 14正式移除；JDK 21完全不支持

  > 官方依据：JEP 363正式移除CMS垃圾收集器。 《JEP 363: Remove the Concurrent Mark Sweep (CMS) Garbage Collector》：https://openjdk.org/jeps/363

### 2. Shenandoah GC

- **定位**：低延迟收集器，由RedHat贡献
- **特点**：并发整理，暂停时间极低；通过Brooks指针实现并发访问
- **版本边界**：部分JDK发行版包含，OpenJDK默认构建通常包含；Oracle JDK部分版本不默认提供
- **适用**：极低延迟需求，且对应JDK发行版支持的场景

### 3. Epsilon GC

- **定位**：无操作垃圾收集器，不执行任何实际回收
- **作用**：仅负责分配内存，不回收；GC开销为0
- **适用场景**：性能测试、微基准测试、短生命周期应用；内存泄漏复现
- **注意**：绝对不能用于生产环境，会很快OOM

### 4. JDK 版本收集器演进表

| JDK版本 | 默认收集器  | 核心变化                            |
| ------- | ----------- | ----------------------------------- |
| JDK 8   | Parallel GC | CMS作为可选，永久代方法区实现       |
| JDK 9   | G1 GC       | G1成为默认，CMS废弃                 |
| JDK 11  | G1 GC       | ZGC实验性引入，元空间全面替代永久代 |
| JDK 14  | G1 GC       | 正式移除CMS                         |
| JDK 15  | G1 GC       | ZGC转正为生产特性                   |
| JDK 17  | G1 GC       | ZGC稳定性增强                       |
| JDK 21  | G1 GC       | 分代ZGC生产就绪，性能大幅提升       |

## 八、主流收集器对比与工程选型

### 1. 主流收集器多维度对比

| 维度           | Serial GC      | Parallel GC         | G1 GC                 | ZGC（分代）              |
| -------------- | -------------- | ------------------- | --------------------- | ------------------------ |
| **核心目标**   | 低开销、简单   | 最高吞吐量          | 平衡吞吐与延迟        | 极低延迟                 |
| **暂停特征**   | 全程STW，长    | 全程STW，多线程缩短 | 多阶段STW，软目标     | 极短STW，微秒级          |
| **吞吐量**     | 低             | 最高                | 高                    | 较高                     |
| **CPU消耗**    | 低             | 中                  | 中高                  | 高                       |
| **内存开销**   | 极低           | 低                  | 中等                  | 较高                     |
| **推荐堆大小** | <1GB           | 2GB~8GB             | 4GB~32GB              | 8GB~16TB                 |
| **典型场景**   | 小程序、嵌入式 | 批处理、离线计算    | 常规Web服务、通用后端 | 低延迟服务、大堆、AI服务 |

### 2. 业务场景选型建议

1. **小型应用/客户端程序**：优先Serial GC，简单稳定开销小
2. **批处理/高吞吐任务**：优先Parallel GC，最大化吞吐量
3. **常规后端Web服务**：优先G1 GC，平衡吞吐与延迟，通用性最强
4. **低延迟在线服务/大堆应用**：优先ZGC，对延迟要求高、堆大、CPU资源充足
5. **AI推理/大模型服务**：优先ZGC，大堆、低停顿，避免GC影响推理延迟

### 3. 选型原则

- 没有万能收集器，必须结合业务目标、堆大小、CPU资源选择
- 优先默认值：无明确需求时优先使用JDK默认的G1
- 先压测再选型：必须基于真实业务压测数据对比，不能仅凭理论选择

## 九、GC 日志与常用排查工具

### 1. GC 日志配置（JDK 21 统一日志框架）

JDK 9+使用`-Xlog`统一日志框架，替代旧版`-XX:+PrintGCDetails`等参数。

**基础配置示例**：

```
java \
  -Xms512m \
  -Xmx512m \
  -Xlog:gc*,gc+heap=debug:file=logs/gc.log:time,uptime,level,tags:filecount=5,filesize=20M \
  -jar app.jar
```

> 说明：运行前确保`logs`目录存在；生产环境根据日志量调整文件大小与数量。 《The java Command, Java SE 21 | Java SE 21 `java` 命令与 JVM 参数文档》：https://docs.oracle.com/en/java/javase/21/docs/specs/man/java.html

**核心日志字段**：

- `time/uptime`：时间戳/运行时长
- `level`：日志级别
- `tags`：日志标签，如`gc`、`gc,young`、`gc,old`
- 暂停时间、回收前后堆占用、GC原因

### 2. 常用排查工具

#### （1）jcmd：多功能JVM诊断命令

**用途**：向运行中的JVM发送诊断命令，功能最全的线上工具。 **常用命令**：

```
# 查看堆信息
jcmd <pid> GC.heap_info

# 查看JVM启动参数
jcmd <pid> VM.flags

# 查看类直方图
jcmd <pid> GC.class_histogram

# 导出堆转储
jcmd <pid> GC.heap_dump /path/to/heap.hprof

# 执行GC
jcmd <pid> GC.run
```

> 官方文档：《Java SE 21 `jcmd` Tool Documentation》：https://docs.oracle.com/en/java/javase/21/docs/specs/man/jcmd.html

#### （2）jstat：GC实时统计

**用途**：持续监控GC指标，观察频率、耗时、内存变化。 **常用命令**：

```
# 每秒采样一次GC汇总，共10次
jstat -gcutil <pid> 1000 10
```

输出核心字段：S0/S1/E/O分别是幸存者区、Eden、老年代使用率；YGC/FGC是次数，YGCT/FGCT是耗时。

> 官方文档：《Java SE 21 `jstat` Tool Documentation》：https://docs.oracle.com/en/java/javase/21/docs/specs/man/jstat.html

#### （3）jmap：堆内存分析

**用途**：导出堆转储、查看类加载统计、对象直方图。 **常用命令**：

```
# 查看类加载统计
jmap -clstats <pid>

# 导出二进制堆转储
jmap -dump:live,format=b,file=heap.hprof <pid>
```

> 注意：堆转储文件可能很大，导出会触发STW，生产环境谨慎执行。 官方文档：《Java SE 21 `jmap` Tool Documentation》：https://docs.oracle.com/en/java/javase/21/docs/specs/man/jmap.html

#### （4）jstack：线程栈分析

**用途**：打印线程栈，排查死锁、阻塞、GC线程状态。 **常用命令**：

```
# 打印线程栈与锁信息
jstack -l <pid>
```

> 官方文档：《Java SE 21 `jstack` Tool Documentation》：https://docs.oracle.com/en/java/javase/21/docs/specs/man/jstack.html

#### （5）JFR（Java Flight Recorder）

**用途**：低开销全量事件采集，可持续线上记录，事后分析GC、方法执行、锁等问题。 **特点**：开销极低（<1%），适合生产环境持续开启；事件级数据，定位问题精准。

## 十、GC 常见故障与诊断流程

### 1. 常见故障场景分析

| 故障现象                 | 可能原因                                       | 排查方向                               |
| ------------------------ | ---------------------------------------------- | -------------------------------------- |
| **Young GC过于频繁**     | 新生代太小、对象分配速率过高、存活对象太多     | 看Eden大小、分配速率、晋升年龄         |
| **Full GC频繁**          | 老年代满、大对象过多、元空间满、内存泄漏       | 看老年代占用、大对象数量、元空间使用率 |
| **GC暂停时间过长**       | 存活对象太多、大对象、引用链复杂、GC线程数不足 | 看存活集大小、Region大小、暂停日志     |
| **堆使用率持续上升**     | 内存泄漏、业务量增长、缓存未过期               | 堆转储分析对象引用链、增长趋势         |
| **GC后存活占比仍很高**   | 长生命周期对象过多、静态集合持有、内存泄漏     | 类直方图、堆转储找大对象               |
| **OOM：Java heap space** | 堆太小、内存泄漏、大对象集中创建               | 保留堆转储，分析泄漏点                 |

### 2. 结构化诊断流程

1. **收集现象**：异常信息、响应时间、吞吐量、CPU、内存、发生时间与频率
2. **确认环境**：JDK版本、收集器类型、JVM参数、容器内存限制
3. **采集证据**：GC日志、jstat趋势、堆转储、JFR记录、业务代码变更
4. **建立假设**：至少列出2~3个可能原因，不直接下定论
5. **验证假设**：通过日志、堆转储、代码分析逐一验证排除
6. **制定方案**：优先修复代码/配置问题，最后调整堆大小与收集器
7. **对照验证**：相同负载下对比调整前后指标
8. **记录结论**：根因、证据、修复措施、验证结果、残余风险

### 3. 核心避坑

- ❌ 只看一条日志就下结论
- ❌ 遇到OOM直接加堆内存
- ❌ 频繁Full GC就换收集器
- ✅ 先排除代码问题、内存泄漏，再调JVM参数

## 十一、GC 参数与调优方法

### 1. 核心参数汇总表

| 参数                              | 作用              | 适用收集器 |
| --------------------------------- | ----------------- | ---------- |
| `-Xms`                            | 初始堆大小        | 通用       |

| `-Xlog:gc*`                       | 开启GC详细日志    | 通用       |

### 2. 调优核心原则

1. **先测量，再调整**：没有数据不调参，先采集基线再优化
2. **优先业务优化**：先优化代码、对象生命周期、缓存策略，再调JVM
3. **一次只改一个参数**：避免多变量混淆，无法归因效果
4. **压测验证**：必须用真实业务压测验证调优效果
5. **避免过度调优**：满足业务目标即可，追求极致收益递减

### 3. 常见调优误区

- ❌ 堆越大越好：堆越大Full GC暂停越长，够用即可
- ❌ 新生代越大越好：新生代大会减少Young GC频率，但增加单次回收时间
- ❌ 暂停时间越短越好：低延迟通常牺牲吞吐量和CPU
- ❌ 频繁GC就是有问题：高分配速率下GC频繁是正常的，看吞吐量和总耗时

### 实验 1：对象分配与年轻代回收

**目标**：观察Young GC触发条件、日志特征与对象分配速率关系。

**测试代码**：

```
import java.util.ArrayList;
import java.util.List;

public class YoungGcDemo {
    public static void main(String[] args) {
        List<byte[]> list = new ArrayList<>();
        for (int i = 0; i < 1000; i++) {
            // 每次分配1MB，总共约1GB
            list.add(new byte[1024 * 1024]);
        }
        // 保持引用，避免立即回收
        System.out.println("分配完成，列表大小: " + list.size());
    }
}
```

**运行命令**：

```
java -Xms256m -Xmx256m -Xlog:gc*,gc+heap=info YoungGcDemo
```

**预期观察**：

- 多次Young GC，Eden满触发
- 每次GC后存活对象晋升到老年代
- 最终老年代满触发Full GC或OOM

**说明**：

- 堆越小，Young GC越频繁
- 保持强引用的对象越多，晋升越多，老年代增长越快

### 实验 5：GC 问题诊断报告（模板）

**报告结构**：

1. **问题现象**：服务响应超时，监控显示Full GC每10分钟一次，堆使用率90%+

2. **环境信息**：JDK21、G1、-Xms4g -Xmx4g、业务为订单查询服务

3. 证据收集

   ：

   - GC日志：老年代回收后占比仍85%，存活对象持续增长
   - jmap直方图：`OrderVO`对象数量异常高
   - 代码排查：本地缓存未设置过期时间

4. **根因定位**：本地缓存无限增长，导致老年代对象过多，频繁Full GC

5. **修复方案**：缓存增加过期时间、最大容量限制；改用Redis分布式缓存

6. **验证结果**：Full GC消失，老年代稳定在40%左右

7. **残余风险**：缓存命中率略有下降，需业务评估可接受

## 十三、面试高频问题与参考答案

### 1. 简单说一下GC的可达性分析？

从GC Roots根对象出发，沿着引用链遍历，能到达的对象标记为存活，不可到达的判定为可回收。解决了引用计数法的循环引用问题，是HotSpot的标准实现。GC Roots主要包括栈局部变量、静态变量、JNI引用等。

### 2. 标记清除、标记复制、标记整理的区别？

- 标记清除：标记存活，直接回收死亡对象；快但碎片多
- 标记复制：分两块，存活对象复制到另一块；无碎片但空间利用率低，适合新生代
- 标记整理：标记后移动存活对象到一端；无碎片空间利用率高，但移动对象开销大，适合老年代

### 3. 分代收集的依据是什么？

基于弱分代假说：绝大多数对象朝生夕死，存活越久越不容易死。所以分成新生代和老年代，新生代用复制算法高频回收，老年代用标记整理低频回收，兼顾效率与开销。

### 4. G1的工作原理？和CMS有什么区别？

G1将堆分成多个Region，每个Region可扮演Eden、Survivor、Old角色。每次优先回收垃圾最多的Region，通过记忆集记录跨区引用。分为Young GC、Mixed GC、Full GC三种。 和CMS比：G1是整理算法，碎片少；可预测暂停时间；不只是老年代，整堆都回收；没有CMS的浮动垃圾和严重碎片问题。

### 5. ZGC为什么这么快？低延迟怎么实现的？

核心是着色指针技术，把对象状态信息存在指针的元数据位里。然后通过负载屏障，读对象的时候处理重定位。大部分标记、重定位工作都和业务线程并发，只有开始结束极短停顿，所以暂停时间在亚毫秒级。

### 6. 什么是STW？所有GC都有STW吗？

STW就是暂停所有应用线程，只跑GC线程。所有GC都有STW阶段，只是时长不同。哪怕ZGC也有标记开始、重定位节点的短暂STW，不是完全没有。

### 7. 什么情况会触发Full GC？怎么避免？

G1中：大对象过多、Mixed GC赶不上分配速度、疏散空间不足、元空间满。 避免：调大堆、减少大对象、优化对象生命周期、调大并发标记线程数。

### 8. 内存泄漏怎么排查？

1. 先看GC日志：老年代占用是不是持续上涨，GC后不下降
2. 导堆转储，用MAT/JProfiler分析大对象、引用链
3. 找长生命周期集合、静态变量、缓存、监听器持有
4. 结合代码定位泄漏点，修复引用释放逻辑

### 9. 怎么选择垃圾收集器？

- 小堆小程序用Serial
- 批处理高吞吐用Parallel
- 通用服务默认G1，平衡最好
- 低延迟大堆用ZGC
- 最终要靠真实压测数据决定，不能只看理论

### 10. System.gc() 有什么用？会立刻执行吗？

只是建议JVM执行GC，不保证立刻执行。一般用在堆转储前、闲时主动回收、测试场景。生产环境通常建议禁用显式GC调用，避免不必要的Full GC。
