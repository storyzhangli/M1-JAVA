### ✅ 核心结论

JDK 17/21 同属新一代LTS，内存结构正式废弃永久代，全面采用元空间实现方法区规范；JDK 17 默认GC为G1，JDK 21 默认升级为ZGC，低延迟能力大幅提升。
**核心区分**：JVM内存区域是**物理运行时的内存划分**，Java内存模型（JMM）是**抽象的并发编程规范**，二者属于完全不同层面的概念，不可混淆。
OOM排查遵循「**现象确认→证据采集→根因定位→修复验证**」四步标准流程，是中高级工程师线上排障的必备能力。

## 一、JVM 内存区域

JVM运行时内存分为「线程私有区域」「线程共享区域」两大块，外加不直接受堆管理的**直接内存**。

### 1. 线程私有区域（随线程创建销毁，不共享）

| 区域                                       | 核心作用                                                     | 常见异常                                                     |
| ------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **程序计数器（Program Counter Register）** | 记录当前线程正在执行的字节码指令地址，字节码解释器通过改变该值选取下一条指令 | 唯一一个不会抛出`OutOfMemoryError`的内存区域                 |
| **虚拟机栈（VM Stack）**                   | 每个方法执行时创建栈帧，存储局部变量表、操作数栈、动态链接、方法出口等信息 | `StackOverflowError`：栈深度超过限制（递归过深）；`OutOfMemoryError`：栈扩展时无法申请到内存 |
| **本地方法栈**                             | 为Native本地方法服务，作用与虚拟机栈一致                     | 同虚拟机栈，部分虚拟机与虚拟机栈合并实现                     |

### 2. 线程共享区域（所有线程共享，全局唯一）

| 区域                      | 核心作用                                                     | 常见异常                                                     |
| ------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **堆（Heap）**            | JVM内存最大的一块，几乎所有对象实例、数组都在此分配；是GC管理的核心区域 | `java.lang.OutOfMemoryError: Java heap space`：最常见OOM，对象无法回收或堆空间不足 |
| **方法区（Method Area）** | JVM规范定义的逻辑区域，存储已加载的类信息、常量、静态变量、JIT编译后的代码等数据 | `java.lang.OutOfMemoryError: Metaspace`                      |
| → **元空间（Metaspace）** | HotSpot虚拟机对方法区的具体实现（JDK8起替代永久代），使用本地内存，不占用堆内存；JDK17/21延续该设计 | 类加载过多、动态生成类（如CGLIB、动态代理）时易溢出          |

### 3. 直接内存（Direct Memory）

- 不属于JVM运行时数据区，也叫堆外内存；通过NIO的`DirectByteBuffer`分配，不受`-Xmx`堆大小限制。
- 优势：减少IO时的内核态/用户态数据拷贝，提升网络/文件IO性能。
- 常见异常：`java.lang.OutOfMemoryError: Direct buffer memory`，通常出现于NIO使用密集、未限制最大直接内存的场景。

>
> 版本说明：JDK8及以后永久代（PermGen）被彻底移除，方法区由元空间实现；JDK17/21均遵循该设计，不存在永久代相关参数。

## 二、Java 内存模型（JMM）

>
> **明确区分**：JMM（Java Memory Model）是一套抽象的**并发编程规范**，用于屏蔽不同硬件架构的内存访问差异，定义多线程环境下读写操作的可见性、有序性、原子性规则；和上一节的物理内存区域是完全不同层面的概念。

### 1. 三大核心特性

| 特性       | 定义                                                         |
| ---------- | ------------------------------------------------------------ |
| **原子性** | 一个操作不可中断，要么全部执行要么完全不执行，中间不会被其他线程打断 |
| **可见性** | 一个线程修改了共享变量，其他线程能立刻看到修改后的最新值     |
| **有序性** | 禁止编译器、处理器为了优化性能对指令进行重排序               |

### 2. happens-before 六大规则

JMM通过happens-before规则定义操作之间的可见性顺序，前一个操作的结果对后一个操作一定可见。

1. **程序顺序规则**：同一线程内，代码前面的操作 happens-before 后面的操作。
2. **监视器锁规则**：对同一把锁的解锁操作，happens-before 后续对该锁的加锁操作。
3. **volatile规则**：对volatile变量的写操作，happens-before 后续对该变量的读操作。
4. **线程启动规则**：线程的`start()`方法，happens-before 该线程内的所有操作。
5. **线程终止规则**：线程内的所有操作，happens-before 该线程的终止检测。
6. **传递性**：A happens-before B，B happens-before C，则A happens-before C。

### 3. 核心应用

`volatile`、`synchronized`、原子类等并发工具的内存语义，本质都是通过happens-before规则保证可见性与有序性。

## 三、GC 核心算法

GC（垃圾回收）的核心目标是自动回收不再被引用的对象内存；基于**弱分代假说**（绝大多数对象朝生夕死，存活时间短）演化出不同算法。

### 1. 四种基础算法

| 算法                          | 核心原理                                                     | 优点                                   | 缺点                                 | 适用场景                         |
| ----------------------------- | ------------------------------------------------------------ | -------------------------------------- | ------------------------------------ | -------------------------------- |
| **标记-清除（Mark-Sweep）**   | 第一阶段标记所有存活对象，第二阶段统一回收死亡对象           | 速度快，不需要移动对象                 | 产生大量内存碎片，大对象可能无法分配 | 老年代，对象存活率高的场景       |
| **标记-整理（Mark-Compact）** | 标记存活对象后，将所有存活对象向一端移动，清理边界外内存     | 无内存碎片，空间利用率高               | 需要移动对象，速度慢，停顿时间长     | 老年代，碎片敏感场景             |
| **复制（Copying）**           | 将内存分为两块，每次只使用一块；回收时将存活对象复制到另一块，清空原块 | 无碎片，分配速度快；复制过程无停顿     | 空间利用率低，只能使用一半内存       | 新生代，对象存活率低、回收频率高 |
| **分代收集**                  | 内存分为新生代、老年代；新生代用复制算法，老年代用标记-清除/整理算法 | 结合各算法优势，适配不同代对象生命周期 | 跨代引用复杂，需要维护卡表           | 主流分代收集器的基础思想         |

### 2. 分代收集基本思想

- **新生代**：对象创建频率高、存活率低，使用复制算法，分为Eden、两个Survivor区，默认比例8:1:1；回收时存活对象复制到另一个Survivor。
- **老年代**：对象存活率高、回收频率低，使用标记-整理或标记-清除算法。
- **对象晋升**：新生代对象熬过多次回收（默认15次）后晋升到老年代；大对象直接进入老年代。

## 四、GC 收集器

### 1. CMS 收集器（历史经典，JDK9废弃）

- **全称**：Concurrent Mark Sweep，并发标记清除收集器
- **基本流程**：初始标记（STW，短）→ 并发标记（和用户线程并行）→ 重新标记（STW，修正并发标记偏差）→ 并发清除
- **核心优势**：低停顿，并发执行大部分GC工作，业务停顿时间短
- **关键代价**：内存碎片严重，长时间运行后可能触发Full GC；CPU占用高；无法处理浮动垃圾
- **适用场景**：低延迟要求的服务，JDK8及以前版本；JDK17/21已彻底移除，不再支持

### 2. G1 收集器（JDK9~JDK17默认）

- **全称**：Garbage-First，垃圾优先收集器
- **核心设计**：将堆划分为多个大小相等的Region块，逻辑上分新生代、老年代，物理上不连续分区
- **基本流程**：初始标记 → 并发标记 → 最终标记 → 筛选回收（优先回收垃圾最多的Region）
- **核心优势**：可预测的停顿时间，兼顾吞吐量与延迟；支持大堆（数GB到数十GB）；整体停顿时间比CMS更可控
- **关键代价**：Region大小固定，大对象会占用多个Region，空间浪费；记忆集维护开销高
- **适用场景**：服务端大堆应用、对延迟有一定要求的业务；JDK17默认收集器

### 3. ZGC 收集器（JDK21默认，JDK17可开启）

- **全称**：Z Garbage Collector，低延迟垃圾回收器
- **核心技术**：着色指针、读屏障、不分代（弱分代）设计；支持TB级堆内存
- **基本流程**：绝大多数标记、移动工作都与用户线程并发，仅在标记开始/结束有极短停顿
- **核心优势**：停顿时间极低（亚毫秒级），几乎不随堆大小增长；大堆下性能优异
- **关键代价**：吞吐量相比G1略有下降；极端小堆场景优势不明显
- **适用场景**：大内存、低延迟要求高的服务，如AI应用、高并发接口服务；JDK21默认收集器

## 五、JVM 调优核心参数（JDK17/21 通用）

| 参数类别       | 常用参数                            | 作用说明                                                     |
| -------------- | ----------------------------------- | ------------------------------------------------------------ |
| **堆大小配置** | `-Xms`                              | 初始堆大小，生产建议与`-Xmx`设为相同值，避免堆动态伸缩       |
|                | `-Xmx`                              | 最大堆大小，核心调优参数                                     |
| **元空间配置** | `-XX:MetaspaceSize`                 | 元空间初始大小                                               |
|                | `-XX:MaxMetaspaceSize`              | 元空间最大值，避免无限制膨胀                                 |
| **GC日志配置** | `-Xlog:gc*`                         | JDK9+统一日志框架，输出GC详细日志；替代旧版`-XX:+PrintGCDetails` |
|                | `-Xlog:gc*:file=gc.log`             | GC日志输出到指定文件                                         |
| **堆转储配置** | `-XX:+HeapDumpOnOutOfMemoryError`   | OOM发生时自动生成堆转储文件，排查必备                        |
|                | `-XX:HeapDumpPath=/path/heap.hprof` | 指定堆转储文件输出路径                                       |
| **直接内存**   | `-XX:MaxDirectMemorySize`           | 限制最大直接内存大小，防止堆外内存溢出                       |
| **收集器指定** | `-XX:+UseG1GC`                      | 强制使用G1收集器                                             |
|                | `-XX:+UseZGC`                       | 强制使用ZGC收集器（JDK21默认）                               |

>
> 工程规范：生产环境必须开启`HeapDumpOnOutOfMemoryError`，OOM现场保留是排障的核心依据。

## 六、OOM 标准排查流程

### 1. 现象确认：先定位OOM类型

从错误日志中识别OOM类型，初步锁定范围：

- `Java heap space`：堆内存溢出，最常见
- `Metaspace`：元空间溢出，类加载相关
- `Direct buffer memory`：直接内存溢出，NIO相关
- `GC overhead limit exceeded`：GC回收效率过低，回收比例不达标，JVM强制抛出

### 2. 证据采集：保留第一现场

1. **堆转储文件（hprof）**：优先使用OOM自动生成的文件；也可通过`jmap -dump:format=b,file=heap.hprof <pid>`手动导出
2. **GC日志**：查看GC频率、回收前后内存、Full GC次数、停顿时间，判断是内存泄漏还是空间不足
3. **线程转储**：`jstack <pid>`，查看线程状态、是否有线程堆积、死锁
4. **运行指标**：堆内存使用率、元空间占用、直接内存占用、类加载数量

### 3. 根因定位：分类排查

| OOM类型               | 常见根因                                                     |
| --------------------- | ------------------------------------------------------------ |
| **堆溢出**            | 1. 内存泄漏：对象被长生命周期引用持有，无法回收（如静态集合、缓存未清理）   2. 大对象过多：一次性加载大量数据、大数组   3. 堆内存配置过小，业务量增长 |
| **元空间溢出**        | 1. 动态生成类过多（CGLIB、动态代理、反射）   2. 类加载器泄漏，重复加载类   3. 元空间上限配置过小 |
| **直接内存溢出**      | 1. NIO直接缓冲区未释放   2. 未配置最大直接内存，默认与堆最大值一致 |
| **GC overhead limit** | 1. 存活对象过多，GC回收占比极低   2. 内存泄漏严重，GC频繁但回收量少 |

### 4. 修复与回归验证

1. **紧急修复**：调大对应内存空间、重启服务临时恢复
2. **根因修复**：释放泄漏引用、优化大对象分批加载、修复类加载器泄漏、限制直接内存大小、优化GC参数
3. **回归验证**：观察监控指标、GC日志，通过压测验证问题不再复现
